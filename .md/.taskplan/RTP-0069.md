# RTP-0069 — Cache do CI no caminho certo e publicação em scripts dedicados (site separado dos dados)

Reserva: Livre
ID no TASK.md: RTP-0069 · Lote: Refatoração Revisão 2026-10-08 · Agente: executor · Chapéu: DevOps · Est: 4h · Dep: - · Status no TASK.md: Pendente
Reqs: G-16, G-18, ADR-015 · Aceite: `actions/cache` do CI usa `processamento/dados/origem` (pasta onde `pnpm baixar-base` grava, porque roda com `--filter processamento`); publicação num script dedicado (ex.: `scripts/publicar.mjs`, Node puro) com passos nomeados, parando no primeiro erro com mensagem do passo, e três comandos: `pnpm publicar:site` roda só build → `wrangler deploy` e não toca no D1; `pnpm publicar:dados` roda preparar, lê o `idPublicacao` do resumo publicado no D1 remoto (consulta só de leitura) e, se for igual ao do `leitura.sql` local, NÃO executa a carga e avisa "dados já publicados", senão executa `wrangler d1 execute --remote`; `pnpm publicar` roda dados e depois site (D1 antes do Worker, ADR-015); `web/PUBLICAR.md` explica quando usar cada um (mudança só em `web/` → `publicar:site`); nenhuma cadeia de `&&` no `package.json`; publicação continua só manual, nunca pelo CI (ARCH-REVIEW 2026-10-08, achados 33 e 34; recarga desnecessária do D1 em correções só de tela consumiu a cota diária em 2026-10-08).

## 1. Plano de execução
**Reaproveitamento:** a chamada ao wrangler sem shell já existe em `processamento/src/cli/publicar-dados.ts` (`execFileSync`, RTP-0038): usar o mesmo padrão (`execFileSync` com array de argumentos, sem `shell: true`). O caminho do `leitura.sql` vem de `processamento/src/config/caminhos.ts` se a RTP-0054 já estiver aprovada; senão, constante única no script.
**Camada:** raiz (`package.json`, `scripts/`), `.github/workflows/ci.yml`.

1. `ci.yml:26-30`: `path: processamento/dados/origem`; a chave continua o SHA-256 da base.
2. `scripts/publicar.mjs` com dois blocos reaproveitáveis, cada passo nomeado:
   - **dados:** `preparar` → ler o `idPublicacao` do documento `resumo` no `leitura.sql` local → consulta só de leitura no D1 remoto (`wrangler d1 execute poc-lab --remote --json --command "SELECT json_extract(conteudo,'$.idPublicacao') FROM documento WHERE chave='resumo'"`) → se iguais, pular a carga com a mensagem "dados já publicados (idPublicacao <hash>)"; se diferentes, ou se a tabela/documento não existir, `wrangler d1 execute --remote --file …/leitura.sql`.
   - **site:** `vite build` → `wrangler deploy`.
   O argumento escolhe `dados`, `site` ou os dois (dados antes, ADR-015).
3. `package.json`: `publicar:dados`, `publicar:site` e `publicar` chamando o script (sem `&&`).
4. `web/PUBLICAR.md`: tabela "o que mudou → qual comando" (só `web/` → `publicar:site`; `processamento/src` → `publicar:dados` ou `publicar`), lembrando que a carga do D1 regrava ~175 mil linhas e reabre a janela de tabela vazia.
5. NÃO acrescentar etapa de backup/volta atrás do D1 aqui: isso depende do BK da revisão sobre troca de dados em produção.

## 2. Plano de teste
- Teste do script com o executor de comandos injetado (sem chamar wrangler de verdade): ordem dos passos e parada no primeiro erro.
- `site`: nenhuma chamada a `wrangler d1`.
- `dados` com hash remoto igual ao local: nenhuma chamada a `d1 execute --file`, mensagem "dados já publicados"; com hash diferente, ou consulta remota sem resultado: a carga roda.
- `publicar` (os dois): dados antes de site.
- Conferir o caminho do cache lendo `processamento/src/cli/baixar-base.ts:21` (`DIR_DESTINO_PADRAO`, relativo à pasta do pacote).
- Comando: `pnpm test`; `pnpm lint`.

## 3. Plano de validação de segurança
G-16: ações continuam fixadas por SHA, `permissions: contents: read`, `persist-credentials: false`; nenhuma publicação a partir do CI; nenhum token do Cloudflare no repositório (G-01). Script sem `shell: true`. Nenhuma dependência nova.
