# TP-0004 — CLI `baixar-base` com URL fixada em commit e SHA-256

Reserva: Livre
ID no TASK.md: TP-0004 · Lote: Lote 1 · Agente: executor · Chapéu: Backend · Est: 1,5h · Dep: TP-0001 · Status no TASK.md: Pendente
Reqs: RNF-05, I-01 · Aceite: Baixa o `.db` para `dados/origem/`; não baixa de novo se o arquivo existir com o hash certo; falha com mensagem clara se o hash divergir; script `pnpm baixar-base`

## 1. Plano de execução
1. Criar `processamento/src/cli/baixar-base.ts`: URL fixa da base de vendas (hardcoded, "fixada em commit" — sem variável de ambiente nem parâmetro de runtime) e SHA-256 esperado também fixo no código (SDD §2 fluxo de preparação passo 1; SDD §6 risco "URL da base de vendas sair do ar").
2. Lógica: se `dados/origem/<arquivo>.db` já existe, calcular SHA-256 do arquivo local; se bater com o hash esperado, não baixar de novo (idempotência) e sair com mensagem informativa; se não bater, falhar com mensagem clara (ex. "hash divergente, arquivo corrompido ou alterado") — não sobrescrever silenciosamente.
3. Se o arquivo não existe, baixar via `fetch` (Node 24 built-in) para `dados/origem/`, depois conferir o SHA-256 do que foi baixado contra o esperado; se divergir, falhar com mensagem clara e não deixar arquivo corrompido no lugar final (baixar para um nome temporário e só mover/renomear após confirmar o hash).
4. Adicionar script `"baixar-base"` em `processamento/package.json` (ou raiz, delegando) chamando este CLI.
5. `dados/` já está no `.gitignore` (TP-0001) — confirmar que o destino cai dentro dessa pasta ignorada.
6. Sem dependência de rede nos testes (TASK §1: "nenhum teste acessa rede além disso") — o teste desta tarefa não pode baixar de fato; ele testa a lógica de conferência de hash com fixture local.
7. Fora de escopo: qualquer leitura do conteúdo do `.db` (isso é TP-0019, Lote 4). Esta tarefa só baixa e confere hash.
8. Ponto de atenção (SDD §2 tabela de incertezas): se a URL ficar instável, documentar download manual no README é tarefa do Lote 14 (TP-0066) — aqui só garantir a mensagem de erro seja clara o bastante para orientar esse caminho futuro.

  - Caso "arquivo já existe com hash certo": criar um arquivo fixture local com conteúdo conhecido, calcular o hash esperado a partir dele, confirmar que a função de conferência não tenta baixar (mock do `fetch` nunca é chamado).
  - Caso "arquivo existe com hash errado": fixture com conteúdo adulterado, confirmar que falha com mensagem clara e não quebra silenciosamente.
  - Caso "arquivo não existe, download simulado": mockar `fetch` para devolver um conteúdo fixture conhecido, confirmar que grava em `dados/origem/` e confere o hash do que foi "baixado".
  - Caso de borda: download mockado que devolve hash divergente do esperado — confirmar falha e que o arquivo final não fica no destino com hash errado (não deixa artefato inválido).
- Comando: `pnpm baixar-base` deve rodar isoladamente nestes testes com `fetch` sempre mockado (nunca rede real), conforme TASK §1.

## 3. Plano de validação de segurança
- Integridade da cadeia de suprimentos (G-16, SDD §7 "Cadeia de suprimentos"): download confere SHA-256 antes de aceitar o arquivo — isso é o próprio objetivo da tarefa; checar que a comparação de hash é feita de ponta a ponta (não só logada, mas usada para decidir falhar).
- Nenhum segredo: a URL é pública e fixa, não é credencial; não há `OPENAI_API_KEY` nem token aqui (G-01).
- Nenhuma escrita fora de `dados/origem/` (que está no `.gitignore`); confirmar que não grava em `dados/origem/` só parcialmente em caso de erro de rede (evitar arquivo truncado ser aceito como válido num próximo run — deve recalcular hash, não só checar existência).
