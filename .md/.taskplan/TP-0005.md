# TP-0005 — CI no GitHub Actions

Reserva: Livre
ID no TASK.md: TP-0005 · Lote: Lote 1 · Agente: executor · Chapéu: DevOps · Est: 1,5h · Dep: TP-0002, TP-0003, TP-0004 · Status no TASK.md: Pendente
Reqs: RF-13, ADR-015 · Aceite: Workflow em push e PR; `ubuntu-latest`, Node 24; ações fixadas por SHA; `permissions: contents: read`; `pnpm install --frozen-lockfile`; base em cache pela chave do SHA-256; `pnpm lint`, `pnpm typecheck`, `pnpm test` (inclui os testes da API, sem conta e sem rede); um passo falhando marca a execução como falha; nenhum segredo nem deploy

## 1. Plano de execução
1. Criar `.github/workflows/ci.yml` com gatilhos `on: [push, pull_request]`.
2. `permissions: contents: read` no topo do workflow (G-16).
3. Job em `runs-on: ubuntu-latest`, `actions/checkout` e `actions/setup-node`/`pnpm/action-setup` fixados por SHA de commit (não por tag `@v4`) — G-16/SDD §7 "Cadeia de suprimentos". Node 24 (`node-version: 24` ou equivalente fixado).
4. Etapa de cache da base de vendas: usar `actions/cache` com chave derivada do SHA-256 fixo usado em `baixar-base` (TP-0004) — reaproveitar entre execuções sem re-baixar sempre; se o cache não existir, o próprio `pnpm test` (que roda `baixar-base` antes, por TASK §1) faz o download real pela única vez.
5. `pnpm install --frozen-lockfile` (nunca `pnpm install` solto) — G-16.
6. Passos subsequentes: `pnpm lint` (TP-0002), `pnpm typecheck` (TP-0001), `pnpm test` (TP-0001/TP-0003/TP-0004, incluindo os testes da API quando existirem em lotes futuros — por ora, os testes existentes do Lote 1). Cada passo roda separado (não um `&&` só) para que o relatório do CI aponte qual falhou.
7. Nenhum passo de deploy, nenhum segredo (`OPENAI_API_KEY`, credencial Cloudflare) referenciado no workflow (G-01, ADR-015: publicação é sempre manual, nunca pelo CI).
8. Confirmar que "um passo falhando marca a execução como falha" é o comportamento padrão do GitHub Actions (steps sequenciais sem `continue-on-error`) — não precisa de lógica extra, só não usar essa flag.
9. Fora de escopo: qualquer step de `wrangler deploy`/`wrangler d1 execute --remote` (isso é proibido aqui e pertence só ao `pnpm publicar` manual do Lote 14).

## 2. Plano de teste
- Verificação é a própria execução do workflow no GitHub (aceite: "execução verde no GitHub"), não um teste unitário local.
- Antes de considerar pronto: abrir um PR (ou push) de teste e confirmar visualmente que o workflow dispara, que os 3 passos (`lint`, `typecheck`, `test`) aparecem e passam.
- Teste negativo: introduzir temporariamente uma falha proposital (ex. quebrar um teste) numa branch isolada para confirmar que o workflow marca a execução como vermelha — depois desfazer, sem deixar a quebra no commit final.
- Confirmar que nenhum teste tenta acessar rede fora do download controlado pela chave de cache/SHA-256 (TASK §1: "sem rede e sem base, falha com 'rode pnpm baixar-base'" — isso é comportamento de `pnpm test` local; no CI, o cache ou o download real supre a base antes).

## 3. Plano de validação de segurança
- G-16 é o núcleo desta tarefa: `permissions: contents: read` explícito, ações fixadas por SHA (não por tag mutável), `--frozen-lockfile` (impede dependência fora do lockfile entrar sem revisão).
- G-01: revisar o `ci.yml` linha a linha confirmando que não há `env` com segredo, não há `secrets.*` referenciado, não há passo de login/deploy.
- ADR-015: confirmar que não existe nenhum step de publicação (D1 remoto ou `wrangler deploy`) — isso seria violação direta de G-19/ADR-015 (publicação só manual, pelo autor).
- Cadeia de suprimentos: confirmar que o cache da base usa a chave do SHA-256 fixo (não algo variável que poderia ser envenenado) e que a conferência de hash do próprio `baixar-base` (TP-0004) ainda roda mesmo com cache hit (não pular a verificação de integridade).
