# TP-0006 — Contrato de evento v1 e tipos do modelo comum

Reserva: Livre
ID no TASK.md: TP-0006 · Lote: Lote 2 · Agente: executor · Chapéu: Backend · Est: 1h · Dep: TP-0001 · Status no TASK.md: Pendente
Reqs: RF-02, RF-09, ADR-006 · Aceite: União discriminada por `tipo` + `versao_schema` (venda, pagamento, coleta, transporte, entrega, todos v1, campos do SDD §5); tipos `Fonte`, `VinculoFonte`, `AchadoQualidade`, `TipoDivergencia`, `Divergencia`; sem I/O

## 1. Plano de execução
1. Criar `processamento/src/dominio/evento.ts`: união discriminada por `tipo` (literais `'venda'|'pagamento'|'coleta'|'transporte'|'entrega'`) + `versao_schema: 1` em cada variante (SDD §5 linha 176-179):
   - `venda` v1: `valor_devido: number`, `data_limite: string` (ISO-8601), `transportadora: string` (forma `Transportadora N`, RNF-04).
   - `pagamento` v1: `valor: number`, `referencia_original: string`. (v2 com `meio_pagamento` é só Lote 17 — não implementar aqui, deixar a união aberta para extensão aditiva futura sem criar o campo agora.)
   - `coleta`/`transporte`/`entrega` v1: `transportadora: string`, `codigo_rastreio: string`.
   - Campos comuns a todo evento (fora da união de payload, conforme `evento` do event store, SDD §5 linha 162): `fonte`, `codigo_evento`, `momento_fato` (ISO-8601 UTC) — decidir se ficam no mesmo tipo `Evento` (envelope) ou em tipo separado; usar um tipo `Evento` que envelopa `{ fonte, codigoEvento, momentoFato }` + a união discriminada de payload, já que TP-0007 (ordenação) e TP-0012 (estado) vão consumir isso.
2. Criar `processamento/src/dominio/modelo.ts` com:
   - `Fonte = 'vendas' | 'pagamentos' | 'rastreio'` (SDD §5 linha 161).
   - `VinculoFonte = { fonte: Fonte, codigoExterno: string, idPedido: string }`.
   - `TipoDivergencia = 'duplicado' | 'parcial' | 'pago_nao_enviado' | 'enviado_nao_pago' | 'entrega_atrasada'` (RN-03 a RN-06; RN-05 produz os dois últimos).
   - `Divergencia = { tipo: TipoDivergencia, motivo: string, idsEventos: string[] }` (TASK §1 "Domínio e regras": toda regra devolve `{ tipo, motivo, idsEventos }` ou nada).
   - `AchadoQualidade = { tipo: TipoAchado, fonte: Fonte, referencia: string, regra: string, detalhe: string }` com `TipoAchado` cobrindo pelo menos os tipos de achado (não-divergência) do gabarito (TASK §1 linha 30): `'fora_de_ordem' | 'sem_identificacao' | 'registro_repetido' | 'linha_invalida' | 'valor_fora_do_padrao'`. Ver nota PENDENTE abaixo sobre a contagem "7 tipos" do TP-0031.
3. Nomes de campos em português/camelCase, exceto quando o tipo espelha coluna do event store (manter consistência com SDD §5, que usa snake_case nas colunas SQL — os tipos TS usam camelCase, sem I/O aqui).
4. Nenhum `import` de `node:*`, `zod` ou outro módulo do projeto (G-02); funções/tipos puros, sem `Date.now()`/`Math.random()` (RNF-05).
5. Fora de escopo: ordenação (TP-0007), cálculo de valores (TP-0008/11), normalização de referência (TP-0010), event store SQL (Lote 4) — aqui só os tipos e a união do evento.

PENDENTE: o critério de aceite do TP-0031 (Lote 6, fora deste lote) fala em "7 tipos" de achado de qualidade, mas o TASK §1 (linha 30, lista do `gabarito.json`) e os critérios dos TP-0013/20/21/22 só enumeram 5 tipos de achado (`fora_de_ordem`, `sem_identificacao`, `registro_repetido`, `linha_invalida`, `valor_fora_do_padrao`) — os outros 5 tipos do gabarito são de divergência. Fixei `TipoAchado` com os 5 tipos encontrados; se houver mais 2 tipos previstos (ex.: achados de formato de data do TP-0020), a tarefa que os introduzir deve estender a união (G-15, aditivo) e isso não bloqueia o TP-0006.

## 2. Plano de teste

  - Checar que `Fonte`, `VinculoFonte`, `AchadoQualidade`, `TipoDivergencia`, `Divergencia` compilam e podem ser usados em um objeto de exemplo de cada um.
