# TP-0007 — RN-07 ordenação canônica dos eventos

Reserva: Livre
ID no TASK.md: TP-0007 · Lote: Lote 2 · Agente: executor · Chapéu: Backend · Est: 1h · Dep: TP-0006 · Status no TASK.md: Pendente
Reqs: RN-07, RF-05 · Aceite: Ordena por `momento_fato`; empate: venda < pagamento < coleta < transporte < entrega, depois `codigo_evento`; qualquer permutação da entrada dá a mesma saída

## 1. Plano de execução
1. Pré-requisito: TP-0006 já define o tipo `Evento` (envelope `{ fonte, codigoEvento, momentoFato, ...payload com tipo }`) em `dominio/evento.ts` — ler esse arquivo antes de implementar (não redeclarar os tipos).
2. Criar `processamento/src/dominio/ordenacao.ts` exportando uma função pura `ordenarEventos(eventos: Evento[]): Evento[]`:
   - Chave primária: `momentoFato` (string ISO-8601 UTC) — comparar como string funciona porque o formato é ISO-8601 UTC fixo (ordenação lexicográfica = ordenação temporal); não usar `new Date()` (evitar dependência de fuso/parsing — mantém pureza e evita bug de `Date` não determinístico entre runtimes).
   - Empate (RN-07, PRD-TECNICO.md linha 143): ordem fixa por `tipo` — `venda` (0) < `pagamento` (1) < `coleta` (2) < `transporte` (3) < `entrega` (4). Usar uma constante `ORDEM_TIPO: Record<TipoEvento, number>` nomeada.
   - Segundo desempate: `codigoEvento` (comparação de string, determinística).
   - Implementar com `Array.prototype.toSorted` ou `[...eventos].sort(...)` (nunca mutar o array recebido — função pura).
3. Não usar `Date.now()`, `Math.random()` nem qualquer I/O (G-02, RNF-05).
4. Fora de escopo: esta tarefa só ordena uma lista já montada de `Evento[]`; não resolve pedido, não calcula estado (isso é TP-0012), não lê de fonte nenhuma.
5. Atenção: a função deve ser *estável* o bastante para que qualquer permutação de entrada produza a mesma saída — como o critério de desempate já é total (tipo, depois código, que é único por `UNIQUE(fonte, codigo_evento)` do event store), não deve haver empate residual; se dois eventos tiverem mesmo `momentoFato`, mesmo `tipo` e mesmo `codigoEvento`, isso seria o mesmo evento (não ocorre na prática).

## 2. Plano de teste
- `processamento/test/dominio/ordenacao.test.ts`, nomeado conforme TASK §1 linha 62: suíte/teste com título `validação: ordenação`.
  - Caso base: lista com 1 evento de cada tipo, `momentoFato` diferentes e fora de ordem cronológica na entrada → saída ordenada por `momentoFato`.
  - Caso de empate: vários eventos com o mesmo `momentoFato` nos 5 tipos, em ordem de entrada aleatória → saída sempre na ordem `venda, pagamento, coleta, transporte, entrega`.
  - Caso de empate dentro do mesmo tipo: dois eventos mesmo `tipo` e mesmo `momentoFato`, `codigoEvento` diferentes → ordena por `codigoEvento` crescente (string).
  - Propriedade "qualquer permutação dá a mesma saída" (exigência literal do critério de aceite): gerar algumas permutações fixas (ex.: 5–10, usando índices embaralhados de forma determinística, não `Math.random()`) da mesma lista de entrada e confirmar que `ordenarEventos` devolve sempre o mesmo array (comparação profunda).
  - Caso de borda: lista vazia → `[]`; lista com 1 elemento → o mesmo elemento.
  - Confirmar que a função não muta o array original (comparar referência/conteúdo antes e depois).
- Comando: `pnpm --filter processamento test -- ordenacao`.
