# TP-0009 — RN-02 quitação e saldo do pedido

Reserva: Livre
ID no TASK.md: TP-0009 · Lote: Lote 2 · Agente: executor · Chapéu: Backend · Est: 1h · Dep: TP-0006 · Status no TASK.md: Pendente
Reqs: RN-02 · Aceite: Dado devido e pagamentos vinculados, devolve pago, saldo e situação (`sem_pagamento`, `parcial`, `quitado`, `excedente`) com tolerância de R$ 0,01

## 1. Plano de execução
1. Criar `processamento/src/dominio/quitacao.ts` exportando função pura `calcularQuitacao(valorDevido: number, pagamentos: number[]): { pago: number, saldo: number, situacao: SituacaoPagamento }`, onde `SituacaoPagamento = 'sem_pagamento' | 'parcial' | 'quitado' | 'excedente'` (exportar o tipo; não está em `modelo.ts` do TP-0006 — decidir se cabe lá; como TP-0006 já fechou sua lista de tipos exportados no critério de aceite, declarar `SituacaoPagamento` aqui mesmo, em `quitacao.ts`, para não reabrir TP-0006).
2. `pago = Σ pagamentos` (soma simples; os valores já vêm de eventos `pagamento` vinculados ao pedido — vínculo e filtragem são de outra camada, fora de escopo aqui: esta função só recebe a lista já filtrada).
3. `saldo = valorDevido − pago` (arredondado a 2 casas só no fim, mesma técnica de TP-0008).
4. Situação (RN-02, PRD-TECNICO.md linha 138, "quitado: |pago − devido| ≤ R$ 0,01"):
   - `pago === 0` → `'sem_pagamento'`.
   - `Math.abs(saldo) <= 0.01` (tolerância) → `'quitado'`.
   - `saldo > 0.01` (e `pago > 0`) → `'parcial'`.
   - `saldo < -0.01` → `'excedente'` (pago > devido; é o caso de RN-03 duplicado, mas essa regra em si é de outra tarefa — TP-0014; aqui só classifica).
5. Tolerância aplicada com comparação numérica direta (`<=`/`>`), não com arredondamento prévio do saldo — importante não arredondar antes de comparar a tolerância, senão R$ 0,004 poderia virar 0,00 e mascarar a regra; comparar o saldo "bruto" (ou arredondado a mais casas que 2, ex. a 4) contra 0,01.
6. Sem I/O, sem `node:*` (G-02). Não resolve vínculo de pagamento (isso é TP-0010), não decide divergência (Lote 3).

## 2. Plano de teste
- `processamento/test/dominio/quitacao.test.ts`:
  - `sem_pagamento`: pagamentos `[]` → pago 0, saldo = devido, situação `sem_pagamento`.
  - `parcial`: devido 100, pagamentos `[40]` → saldo 60, situação `parcial`.
  - `quitado` exato: devido 100, pagamentos `[100]` → saldo 0, `quitado`.
  - `quitado` com tolerância: devido 100, pagamentos `[99.995]` ou `[100.005]` → dentro de R$ 0,01, `quitado`.
  - Borda da tolerância: devido 100, pagamentos `[99.98]` (saldo 0,02 > 0,01) → `parcial`, não `quitado` — fronteira exata importa.
  - `excedente`: devido 100, pagamentos `[80, 80]` (parcelas que somam mais que devido) → saldo negativo, `excedente`.
  - Caso de parcelas que quitam exatamente somando: devido 100, pagamentos `[60, 40]` → `quitado` (cobre a nota de RN-04 "parcelas que quitam não geram divergência", relevante para TP-0015 mais tarde, mas o cálculo correto de saldo é testado aqui).
