# TP-0010 — RN-09 normalização e casamento da referência de pagamento

Reserva: Livre
ID no TASK.md: TP-0010 · Lote: Lote 2 · Agente: executor · Chapéu: Backend · Est: 1,5h · Dep: TP-0006 · Status no TASK.md: Pendente
Reqs: RN-09, RF-03 · Aceite: Remove prefixo, espaços e zeros à esquerda; vincula só se casar com exatamente 1 código conhecido; texto livre e referência com dois códigos dão "sem identificação"

## 1. Plano de execução
1. Criar `processamento/src/dominio/referencia.ts` com duas funções puras:
   - `normalizarReferencia(referencia: string): string[]` — extrai candidato(s) de código de pedido da referência bruta: remove o prefixo `PV-` (TASK §1 linha 28: "`referencia` normalmente `PV-` + código de vendas com zeros à esquerda e espaços variados"), remove espaços (inclusive internos/nas pontas) e zeros à esquerda do número restante. Como o critério de aceite cita "referência com dois códigos" como caso plantado, a função deve ser capaz de **extrair mais de um candidato** quando a referência bruta contiver dois números reconhecíveis (ex. dois trechos separados por algo, ou dois códigos concatenados) — devolver todos os candidatos encontrados, não só o primeiro.
   - `casarReferencia(referencia: string, codigosConhecidos: Set<string>): { idPedido: string } | { semIdentificacao: true }` — chama `normalizarReferencia`, filtra os candidatos que batem com `codigosConhecidos`; se exatamente 1 candidato bater → vínculo; se 0 ou ≥ 2 baterem → `semIdentificacao: true` (RN-09, PRD-TECNICO.md linha 145: "Texto livre ou casamento com mais de um candidato vira 'sem identificação'").
2. "Código conhecido" aqui é um `Set<string>` de códigos de pedido já normalizados, passado pela camada chamadora (fonte real desses códigos é a base de vendas — isso é responsabilidade do adaptador `fontes/pagamentos.ts`, TP-0021, fora de escopo; esta tarefa só recebe o conjunto já pronto).
3. Tratar "texto livre" (sem nenhum padrão numérico reconhecível) como 0 candidatos → `semIdentificacao`.
4. Função pura, determinística, sem I/O, sem regex dependente de locale, sem `node:*` (G-02).
5. Fora de escopo: ler o CSV (TP-0021), decidir achado de qualidade a partir do resultado (isso é efeito colateral de outra camada — aqui a função só devolve o resultado do casamento).

## 2. Plano de teste
- `processamento/test/dominio/referencia.test.ts`:
  - `PV-000123` com espaços variados (`" PV-000123 "`, `"PV- 000123"`) → normaliza para `"123"` (ou identidade comparável ao código conhecido sem zeros à esquerda).
  - Zeros à esquerda: `PV-0000045` → `"45"`.
  - Casamento único: referência normalizada bate com exatamente 1 código do conjunto conhecido → vínculo com o `idPedido` certo.
  - Texto livre sem nenhum número reconhecível (ex. `"pagamento do pedido via boleto"`) → `semIdentificacao: true`.
  - Referência com dois códigos (ex. `"PV-000123 PV-000456"` ou equivalente plantado) → `semIdentificacao: true`, mesmo que ambos os códigos existam no conjunto conhecido.
  - Candidato que não bate com nenhum código conhecido (0 candidatos válidos) → `semIdentificacao: true`.
  - Caso de borda: referência vazia ou só espaços → `semIdentificacao: true`.
- Comando: `pnpm --filter processamento test -- referencia`.

## 3. Plano de validação de segurança
Função pura de parsing/casamento de string, sem I/O — a entrada (`referencia`) vem de um CSV gerado/importado localmente, não de usuário remoto; ainda assim, trata entrada "suja" por natureza (RN-09 existe exatamente para não confiar ciegamente no dado). Mínimo aplicável:
- Nenhuma dependência nova (G-17) — implementar sem lib de regex externa.
- Confirmar no diff que não há `node:*`/`zod`/import de outro módulo (G-02).
- Garantir que a extração de candidatos não usa regex vulnerável a *catastrophic backtracking* (ReDoS) — preferir padrões simples e ancorados (ex. `/\d+/g` com limite de repetição implícito pelo tamanho da string, já limitada pelo CSV); revisar manualmente a regex escolhida.
- Nenhum dado pessoal: referência é código de pedido sintético, não há PII.
