## 1. Plano de execução
1. Criar `processamento/src/dominio/valores-fora-do-padrao.ts` com funções puras separadas para os dois contextos do RN-10 (PRD-TECNICO.md linha 146):
   - `verificarItemPedido(item: { precoUnitario: number, quantidade: number, desconto: number }): AchadoValorForaDoPadrao | null` — detecta: `precoUnitario <= 0`, `quantidade <= 0`, `desconto < 0 || desconto > 1`. Se qualquer uma falhar, devolve achado com `regra` em texto simples explicando qual condição falhou e os valores (TASK §1 linha 33: "`motivo` em linguagem simples, com os valores").
   - `verificarPagamento(valorPagamento: number, valorDevido: number): AchadoValorForaDoPadrao | null` — detecta: `valorPagamento <= 0`, `valorPagamento > 2 * valorDevido`.
2. Tipo de retorno `AchadoValorForaDoPadrao` (local a este arquivo, ou reaproveitando o formato `{ tipo: 'valor_fora_do_padrao', regra: string, detalhe: string }` alinhado com `AchadoQualidade` do TP-0006 — usar o mesmo `tipo` fixo `'valor_fora_do_padrao'` do TP-0006 para que os adaptadores (Lote 4) consigam empilhar isso direto em `AchadoQualidade`; os campos `fonte`/`referencia` ficam a cargo do adaptador, que tem esse contexto — aqui só `regra` e `detalhe`, ou um achado "parcial" sem `fonte`/`referencia` que o adaptador completa).
3. Se múltiplas condições falharem no mesmo item/pagamento, decidir se devolve 1 achado consolidado (texto cita todas as falhas) ou lista de achados — critério de aceite fala em achado singular por verificação; optar por **um achado por chamada**, com `detalhe` listando todas as condições violadas naquele item/pagamento (mais simples, cobre o aceite sem ambiguidade).
4. Sem I/O, sem `node:*` (G-02). Não decide se o achado é gravado (isso é dos adaptadores, Lote 4) — aqui só a regra pura.

  - Cada achado contém o(s) valor(es) concretos na mensagem (verificar substring do valor no texto).
