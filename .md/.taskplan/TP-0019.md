# TP-0019 — Leitura somente leitura da base de vendas e normalização das datas

Reserva: Livre
ID no TASK.md: TP-0019 · Lote: Lote 4 · Agente: executor · Chapéu: Backend · Est: 2h · Dep: TP-0004, TP-0006 · Status no TASK.md: Pendente
Reqs: RF-01, RF-04 · Aceite: Abre o `.db` só para leitura; devolve pedidos com itens, data do pedido em ISO classificada `curto`/`longo`, data de envio, data limite e código da transportadora; com a base real: 16.282 pedidos, 609.283 itens, 830 curto, 15.452 longo, 21 sem envio

## 1. Plano de execução
1. Criar `processamento/src/fontes/leitura-vendas.ts`. Abrir o `.db` baixado por TP-0004 (`dados/origem/`) usando `node:sqlite` em modo **somente leitura** (ex. `DatabaseSync(caminho, { readOnly: true })` — confirmar flag exata na API do `node:sqlite` usada no projeto; se a versão de Node não tiver flag de read-only nativa, documentar a limitação e garantir pelo código que nenhum `INSERT/UPDATE/DELETE` é emitido contra essa conexão).
2. Consultar a base de vendas (schema real da base, inspecionar `dados/origem/*.db` ou usar o que TP-0004 documentou) e devolver uma lista de pedidos com: itens (preço, quantidade, desconto), data do pedido convertida para ISO-8601 (classificando o formato original de origem como `curto` ou `longo` conforme os dois formatos de data presentes na base — ver RF-04/achados de qualidade), data de envio (pode ser nula — 21 pedidos sem envio), data limite, código da transportadora (cru, sem tradução para `Transportadora N` — essa tradução é RN responsabilidade do adaptador TP-0020).
3. Esta função só lê e normaliza formato de data; NÃO cria eventos de domínio nem calcula valor devido (isso é TP-0020). NÃO classifica achados de qualidade (isso também é TP-0020, que consome esta leitura).
4. Sem I/O fora deste módulo: `fontes/` pode usar `node:*` (não é `dominio/` nem `contrato/`).
5. Depende de TP-0004 (arquivo `.db` já baixado) e TP-0006 (tipos do domínio, se reaproveitados para o retorno).
6. Atenção: os números do critério de aceite (16.282 pedidos, 609.283 itens, 830 curto, 15.452 longo, 21 sem envio) são a base real baixada por `pnpm baixar-base` — o teste de integração deve rodar contra ela, não contra fixture sintética.

Comando: `pnpm --filter processamento test test/integracao/leitura-vendas.test.ts` (base real já baixada em `processamento/dados/origem/northwind.db`).
Resultado antes da correção: 6/7 passaram; o teste "não lança e não grava nada na base real ao ler (round-trip de leitura)" falhou por **timeout** (5000ms default do Vitest) — a função chama `lerBaseDeVendas` duas vezes dentro do próprio teste (mais uma vez já executada na raiz do describe anterior), e cada chamada processa 609.283 itens/16.282 pedidos reais, levando ~4,4s por chamada. Resultado final: `pnpm --filter processamento test test/integracao/leitura-vendas.test.ts` → 7/7 testes passaram (16.282 pedidos, 609.283 itens, 21 sem envio, classificação curto/longo confirmada). PASS (corrigido).
