# TP-0020 — Adaptador de vendas: vínculos, evento `venda` e achados

Reserva: Livre
ID no TASK.md: TP-0020 · Lote: Lote 4 · Agente: executor · Chapéu: Backend · Est: 2h · Dep: TP-0008, TP-0011, TP-0019 · Status no TASK.md: Pendente
Reqs: RF-02, RN-01, RN-10 · Aceite: Para cada pedido: vínculo (`vendas`, código), evento `venda` v1 com valor devido, data limite e `Transportadora N`; achados de data por formato, pedido sem envio e item fora do padrão

## 1. Plano de execução
1. Criar `processamento/src/fontes/vendas.ts`, o adaptador explícito de vendas chamado pelo caso de uso `importar` (TASK.md §1: "Os 3 adaptadores são chamados explicitamente pelo caso de uso importar. Proibido criar interface/registro genérico de 'fonte'" — ADR-005).
2. Para cada pedido devolvido por `fontes/leitura-vendas.ts` (TP-0019):
   - Montar `VinculoFonte` `{ fonte: 'vendas', codigo_externo: <código do pedido na base>, ... }`.
   - Calcular `valor_devido` usando `dominio/valores.ts` (TP-0008, RN-01: Σ preço × quantidade × (1 − desconto), arredondado só no fim).
   - Montar evento `venda` v1 (`dominio/evento.ts`, TP-0006) com `valor_devido`, `data_limite`, `transportadora` traduzida para `Transportadora N` pelo código da base (RNF-04, TASK.md §1 L-02) — nunca o nome original.
   - Gerar achados: data de formato `curto`/`longo` (vindo de TP-0019), pedido sem data de envio (achado específico), item fora do padrão usando `dominio/valores-fora-do-padrao.ts` (TP-0011, RN-10).
3. `transportadora` deve ser mapeada por código→`Transportadora N` de forma estável (ex. ordenar códigos únicos encontrados e numerar, ou usar tabela fixa se o SDD especificar — conferir se há mapa fixo nos ADRs; se não houver, numerar por ordem de primeira aparição determinística, respeitando RNF-05 de determinismo).
4. NÃO grava no SQLite (isso é `importar`, TP-0027, que usa `armazenamento/repositorio.ts` de TP-0018). Esta tarefa só transforma dados lidos em `VinculoFonte[]`, `Evento[]` e `AchadoQualidade[]` em memória, puro a partir da leitura.
5. Depende de TP-0008 (RN-01), TP-0011 (RN-10) e TP-0019 (leitura). Paralelizável com TP-0018, TP-0021, TP-0022.
6. Atenção: `dominio/` é puro (TASK.md §1) — os cálculos de valor/achados ficam em `dominio/`, o adaptador só orquestra leitura + chamada ao domínio + montagem do evento/vínculo.

## 2. Plano de teste
- `processamento/test/fontes/vendas.test.ts`.
- Caso: pedido simples sem problema → 1 vínculo `vendas`, 1 evento `venda` v1 com `valor_devido` correto (RN-01), `transportadora` no formato `Transportadora N`.
- Caso: pedido com data em formato `curto` e outro em `longo` → achado de data correspondente a cada um.
- Caso: pedido sem data de envio → achado "pedido sem envio" (contagem deve bater com os 21 da base real, verificável no teste de integração do Lote 5/7, aqui testar unidade com fixture).
- Caso: item com preço ≤ 0 ou desconto fora de [0,1] → achado de item fora do padrão (RN-10), via TP-0011.
- Caso de borda: dois pedidos com o mesmo código de transportadora → mesmo `Transportadora N` (mapeamento estável).
- Determinismo: mesma entrada (fixture) chamada 2x → mesma saída byte a byte (sem `Date.now()`/`Math.random()`).
- Rodar: `pnpm --filter processamento test test/fontes/vendas.test.ts`.

## 3. Plano de validação de segurança
Sem superfície de rede/usuário (processamento local, dados confiáveis da base própria). Mínimo a verificar:
- Nenhum nome real de transportadora chega ao evento/vínculo gerado — só `Transportadora N` (RNF-04, GUARDRAILS G-11); checar no diff que não há vazamento do nome original em mensagens de achado.
- `dominio/` continua sem I/O/`zod`/`node:*` — conferir imports do que for colocado em `dominio/valores.ts`/`valores-fora-do-padrao.ts` nesta tarefa.
- Nenhum dado é descartado silenciosamente sem gerar achado (RN-10 cobre consistência de qualidade, não segurança, mas documentar se achar lacuna).
