# TP-0021 — Adaptador de `pagamentos.csv`

Reserva: Livre
ID no TASK.md: TP-0021 · Lote: Lote 4 · Agente: executor · Chapéu: Backend · Est: 2,5h · Dep: TP-0010, TP-0011 · Status no TASK.md: Pendente
Reqs: RF-02, RN-09, RN-10 · Aceite: Lê com `csv-parse`; linha inválida vira achado `linha_invalida` sem parar; mesmo `codigo_transacao` repetido vira `registro_repetido`; referência resolvida por RN-09 (sem casamento = evento sem pedido + achado `sem_identificacao`); valor fora do padrão vira achado

## 1. Plano de execução
1. Criar `processamento/src/fontes/pagamentos.ts`, adaptador explícito de pagamentos (ADR-005, mesma regra de não-genericidade do TP-0020).
2. Ler `pagamentos.csv` com `csv-parse` (biblioteca já prevista no SDD §3 — confirmar que está listada; se não estiver, é dependência nova e deve ser sinalizada). Formato do CSV (TASK.md §1): `codigo_transacao,referencia,valor,data_pagamento` (+ `meio_pagamento` opcional, só Lote 17 — ignorar aqui).
3. Para cada linha:
   - Linha malformada (campos faltando, data inválida, valor não numérico etc.) → não lança erro, gera achado `linha_invalida` (um dos 7 tipos do documento `qualidade`, TP-0031/TP-0038) e **não** produz evento para essa linha; segue processando as demais.
   - `codigo_transacao` repetido (já visto nesta importação) → achado `registro_repetido`, evento não duplicado (ou registrado só uma vez, dependendo de como o event store trata — mas aqui o adaptador deve sinalizar a repetição para quem for gravar).
   - Resolver `referencia` usando `dominio/referencia.ts` (TP-0010, RN-09): normaliza prefixo/espaços/zeros à esquerda; casa com exatamente 1 código conhecido de vendas → vincula; texto livre ou referência com 2 códigos → achado `sem_identificacao` e evento de pagamento **sem** `id_pedido` (campo nulo, conforme schema `evento` do SDD §5).
   - Valor fora do padrão (RN-10, via TP-0011: pagamento ≤ 0 ou pagamento > 2× devido — este último precisa do valor devido do pedido já vinculado, então essa checagem específica de ">2× devido" pode depender de dado externo ao CSV; se o pedido ainda não foi resolvido nesta etapa, considerar se a checagem completa de RN-10 para pagamentos acontece aqui ou mais adiante no caso de uso `importar`/domínio — seguir o que TP-0011 já define como função pura recebendo os dados necessários).
4. Devolver `{ vinculos: VinculoFonte[], eventos: Evento[], achados: AchadoQualidade[] }`, puro em memória — sem gravar no SQLite (isso é TP-0027/TP-0018).
5. Depende de TP-0010 (RN-09) e TP-0011 (RN-10). Paralelizável com TP-0018, TP-0019, TP-0020, TP-0022.
6. Atenção: `csv-parse` só é usado aqui (`fontes/`), nunca em `dominio/`. NÃO implementar a gravação idempotente (TP-0018) nem o orquestrador de importação (TP-0027).

## 3. Plano de validação de segurança
Entrada é um CSV de dados sintéticos/gerados localmente, não input de usuário remoto — risco baixo, mas CSV é superfície de parsing que merece atenção a robustez:
- Confirmar que `csv-parse` é chamado sem opções perigosas (ex. não usar `eval`/execução de fórmula — CSV injection não se aplica aqui pois não há exportação para planilha, mas vale registrar).
- Linha malformada nunca deve lançar exceção não tratada que pare a importação inteira (RF-02 exige continuidade) — isso é também requisito funcional, mas tem efeito de robustez/disponibilidade.
- Nenhum dado de pagamento (valor, referência) é logado em texto claro além do necessário para achados (achados já fazem parte do contrato, então não é vazamento, mas confirmar que não há log adicional fora do fluxo de achados).
- `csv-parse` como dependência nova: confirmar que está no SDD §3/GUARDRAILS G-17 (lista de permitidas) antes de instalar; se não estiver, sinalizar como desvio antes de prosseguir.
