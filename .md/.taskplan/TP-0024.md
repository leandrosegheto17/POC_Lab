# TP-0024 — Gerador base: `rastreio.csv` sem problemas

Reserva: Livre
ID no TASK.md: TP-0024 · Lote: Lote 5 · Agente: executor · Chapéu: Backend · Est: 2h · Dep: TP-0023 · Status no TASK.md: Pendente
Reqs: RF-01, ADR-009 · Aceite: Para cada pedido com data de envio: `coleta` na data de envio, `transporte` e `entrega` até a data limite (§6 L-05), linhas na ordem canônica; formatos da §1; integrado ao `pnpm gerar`; determinismo byte a byte mantido

## 1. Plano de execução
1. `gerador/rastreio.ts`: para cada pedido com data de envio (de `fontes/leitura-vendas.ts`, TP-0019 — os 21 pedidos sem envio da base real não geram nada aqui), gerar 3 eventos: `coleta` na data de envio; `transporte` numa data intermediária escolhida pelo PRNG (TP-0023) entre a coleta e a data limite; `entrega` numa data ≤ data limite — decisão L-05 (TASK.md §6): "o gerador cria `transporte` e `entrega` a partir da data de envio, dentro da data limite nos pedidos limpos".
2. Escrever `rastreio.csv` com cabeçalho `codigo_evento,codigo_rastreio,pedido_venda,tipo,momento_fato,transportadora` (TASK.md §1): `codigo_evento` sequencial determinístico; `codigo_rastreio` = `RS-` + 6 dígitos (1 por pedido, reaproveitado nos 3 eventos do mesmo pedido); `tipo` ∈ `coleta`/`transporte`/`entrega`; a ordem das linhas no arquivo é a ordem canônica de geração (coleta, transporte, entrega, pedido a pedido) — TASK.md §1 "a ordem das linhas é a ordem de chegada".
3. Integrar ao `gerador/gerar.ts` (TP-0023): depois de escrever `pagamentos.csv`, chamar o escritor de `rastreio.csv` na mesma execução de `pnpm gerar`.
4. Usar a mesma instância do PRNG (`mulberry32`) de TP-0023 sem reiniciar a semente no meio — isso garante que a sequência de números não se repete entre pagamentos e rastreio (senão duas chamadas diferentes consumiriam os mesmos números, achatando a aparente aleatoriedade; documentar a ordem de consumo do PRNG se mudar).
5. NÃO plantar nenhum problema de rastreio aqui (fora de ordem, atraso, linha inválida) — isso é TP-0026. Aqui só a base "limpa".
6. Atenção a `transportadora`: já vem traduzida `Transportadora N` por `fontes/vendas.ts` (TP-0020); aqui só repassar o valor do pedido, nunca o nome original (RNF-04, G-11).

## 2. Plano de teste
- `processamento/test/integracao/gerador.test.ts` (mesmo arquivo de TP-0023, acrescentar casos).
- Pedido com data de envio → 3 linhas (`coleta`, `transporte`, `entrega`) com `momento_fato` em ordem crescente e `entrega` ≤ data limite.
- Pedido sem data de envio (ex. fixture simulando os 21 da base real) → 0 linhas em `rastreio.csv` para esse pedido.
- `codigo_rastreio` é o mesmo nas 3 linhas do mesmo pedido, formato `RS-\d{6}`.
- Ordem das linhas no arquivo é a ordem canônica (coleta, transporte, entrega por pedido, pedidos na ordem de geração).
- Determinismo: `pnpm gerar --semente 20261007` 2x → `rastreio.csv` byte a byte idêntico.
- Rodar: `pnpm --filter processamento test test/integracao/gerador.test.ts`.

## 3. Plano de validação de segurança
Sem superfície de rede/usuário (gerador local). Mínimo a verificar:
- Nenhum nome de transportadora original no CSV gerado — só o valor já traduzido `Transportadora N` (RNF-04, G-11); checar no diff.
- Sem dependência nova (G-17); sem `Math.random()`/`Date.now()` (G-10).
- `gabarito.json` continua não lido fora de `test/` (G-04) — esta tarefa não grava gabarito (não planta problema).

## Verificação (2026-10-08)
Implementação já existente verificada. `gerador/rastreio.ts` (base "limpa" do rastreio) estava correto isoladamente (3 linhas coleta/transporte/entrega, ordem canônica, `codigo_rastreio` reaproveitado, sem nome real de transportadora, determinismo byte a byte) — os 7 testes de `gerarRastreio` em `gerador.test.ts` já passavam sem alteração.
- Achado (fora do escopo direto de TP-0024, mas descoberto ao rodar TP-0028 contra a base real): a base real (`northwind.db`) tem ~3.755 pedidos cuja `dataEnvio` é POSTERIOR à própria `dataLimite` (atraso já presente nos dados de origem, não plantado). Como `gerarRastreio` interpola `transporte`/`entrega` entre `dataEnvio` e `dataLimite`, nesses pedidos a `entrega` sempre cai depois da `dataLimite` — uma divergência `entrega_atrasada` legítima, mas que não nasce de nenhum plantio (TP-0025/26) e por isso não entrava no `gabarito.json`, causando falso positivo no teste de M1 (TP-0028). Correção aplicada em `gerador/divergencias-naturais.ts` (nova, chamada por `cli/gerar.ts`): registra essas ocorrências no gabarito como achado "natural" (não plantado), sem alterar `gerador/rastreio.ts` nem a regra de domínio (RN-06) — decisão alinhada a ADR-009 ("corrigir o gerador, nunca a regra de domínio" quando a colisão é com divergência natural da base real). Nenhum código desta tarefa (TP-0024) foi alterado.
- Comando: `pnpm --filter processamento test test/integracao/gerador.test.ts` → 32/32 passando. Comando: `pnpm --filter processamento test test/integracao/gabarito.test.ts` (pipeline completo contra a base real) → 2/2 passando, 0 falso positivo/negativo (ver nota em TP-0028).
