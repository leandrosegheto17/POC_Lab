# TP-0030 — Esquemas de resposta v1: resumo, divergências e linha do tempo

Reserva: Livre
ID no TASK.md: TP-0030 · Lote: Lote 6 · Agente: executor · Chapéu: Backend · Est: 2h · Dep: TP-0029 · Status no TASK.md: Pendente
Reqs: ADR-016, RF-05, RF-07, RF-11, UX-SPEC §2 · Aceite: `resumo` com data de corte, semente, versão do contrato, identificador da publicação e `totais` (pedidos, pedidos com divergência, contagem por tipo, valor em aberto, pago a mais, entregas no prazo — cada cartão com fórmula, numerador, denominador; §6 L-07); `divergencias` paginada (`dados[]` com pedido, tipo, motivo, eventos); linha do tempo v1 (pedido: identidade, código buscado, fontes e códigos, devido, pago, data limite, divergências; eventos na forma v1 **sem** `versao_schema` e com `chegouForaDeOrdem`); o esquema de evento v1 descarta campo desconhecido (teste com `meio_pagamento` extra)

## 1. Plano de execução
1. `processamento/src/contrato/resumo.ts`: `EsquemaResumo = z.object({ dataCorte: z.string(), semente: z.number().int(), versaoContrato: z.string(), idPublicacao: z.string(), totais: EsquemaTotais })`. TASK §1 ("Todo indicador e todo cartão de resumo é um bloco com fórmula, numerador, denominador e resultado") exige que cada total seja um cartão, não um número solto: `EsquemaCartao = z.object({ titulo: z.string(), formula: z.string(), numerador: z.number(), denominador: z.number(), resultado: z.number().nullable() })` (`resultado` nulo quando `denominador === 0`). `EsquemaTotais = { pedidos: EsquemaCartao, pedidosComDivergencia: EsquemaCartao, porTipo: z.array(z.object({ tipo: <TipoDivergencia>, cartao: EsquemaCartao })), valorEmAberto: EsquemaCartao, pagoAMais: EsquemaCartao, entregasNoPrazo: EsquemaCartao }`.
2. Decisão a documentar: o "cartão" do resumo e o "bloco de indicador" do TP-0031 têm a mesma forma (fórmula/numerador/denominador/resultado), mas TP-0030 e TP-0031 são paralelizáveis sem dependência entre si (TASK §4) — por isso cada arquivo define seu próprio tipo zod local (`EsquemaCartao` aqui, bloco do indicador em `contrato/indicadores.ts`), sem import cruzado. Se depois quiserem extrair um `contrato/bloco.ts` comum, é refactor fora desta tarefa.
3. `processamento/src/contrato/divergencias.ts`: `EsquemaEventoDivergencia = z.object({ tipo: z.string(), data: z.string(), fonte: <Fonte de dominio/modelo.ts>, codigo: z.string() })` (espelha `divergencia.eventos` JSON do SDD §5 linha 173); `EsquemaRespostaDivergencias = z.object({ dados: z.array(z.object({ pedido: z.string(), tipo: <TipoDivergencia>, motivo: z.string(), eventos: z.array(EsquemaEventoDivergencia) })), paginacao: EsquemaPaginacao })` (reusa `contrato/paginacao.ts`, TP-0029).
4. `processamento/src/contrato/linha-do-tempo-v1.ts`: `EsquemaEventoV1` = união discriminada por `tipo`, campos v1 de `dominio/evento.ts` (TP-0006) **menos** `versao_schema`, **mais** `chegouForaDeOrdem: z.boolean()`; usar `z.object()` simples (não `.strict()`) em cada variante para que campo desconhecido (ex. `meio_pagamento` da v2) seja silenciosamente descartado no `.parse()` — é o mecanismo concreto de G-21 ("a v1 entrega os eventos na forma v1... o esquema descarta campos posteriores"). `EsquemaLinhaDoTempoV1 = z.object({ pedido: z.object({ identidade: z.string(), codigoBuscado: z.string(), fontes: z.array(z.object({ fonte: <Fonte>, codigo: z.string() })), devido: z.number(), pago: z.number(), dataLimite: z.string(), divergencias: z.array(z.object({ tipo: <TipoDivergencia>, motivo: z.string() })) }), eventos: z.array(EsquemaEventoV1) })`.
5. Reaproveitar `TipoDivergencia`/`Fonte` de `dominio/modelo.ts` (TP-0006) em todos os enums — nunca redeclarar literais (TASK §1 linha 13).
6. Fora de escopo: `/api/v2` (TP-0076, Lote 17/Should), uso real nas rotas (TP-0046/47/48), projeções que preenchem esses dados (Lote 7).
7. Ponto de atenção: o arquivo de teste `test/contrato/respostas-v1.test.ts` é **compartilhado** com TP-0031 (mesma tarefa paralela, mesmo arquivo na coluna Testes do TASK.md) — ler o arquivo imediatamente antes de editar e usar `Edit` (nunca `Write`) para não sobrescrever o `describe` da outra tarefa; se o `Edit` falhar por conteúdo mudado, reler e refazer.

## 3. Plano de validação de segurança
- Estes esquemas são a última barreira antes de qualquer resposta 200 sair do Worker (G-08: "toda resposta 200 passa pelo esquema de resposta antes de sair") e o mecanismo que garante G-21 (v1 nunca muda de forma) — conferir que nenhuma variante usa `.passthrough()` (isso reabriria a v1 a campo desconhecido).
- Nenhum nome de transportadora original pode aparecer nesses esquemas — campos de transporte são só os já tipados em `dominio/evento.ts` (`transportadora: string`, que a camada de publicação já preenche como `Transportadora N`, G-11); este esquema não precisa (e não deve) validar o *conteúdo* da string, só a forma.
- Sem segredo, sem dado pessoal, sem dependência nova.
