# TP-0035 — Projeção de `pedido_resumo` e `vinculo_codigo`

Reserva: Livre
ID no TASK.md: TP-0035 · Lote: Lote 7 · Agente: executor · Chapéu: Backend · Est: 2h · Dep: TP-0027, TP-0029, TP-0032 · Status no TASK.md: Pendente
Reqs: RF-03, RF-05, M2 · Aceite: Uma linha por pedido (devido, pago, data limite, situação, fontes → código em JSON de chaves ordenadas); uma linha por código normalizado (`normalizarCodigo`) de cada fonte e pela identidade `PED-`; colisão de código normalizado faz a publicação falhar com mensagem; nenhum nome da base além de `Transportadora N`

## 1. Plano de execução
1. Criar `processamento/src/publicacao/pedidos.ts`.
2. Ler do event store local todos os pedidos, vínculos (`vinculo_fonte`) e eventos gravados por `importar` (TP-0027) — usar/estender as funções de leitura de `armazenamento/repositorio.ts` (TP-0018, que hoje só define gravação); qualquer leitura nova de SQLite continua restrita a `armazenamento/` (G-05) — se precisar adicionar função de leitura ali, registrar no resultado da execução.
3. Para cada pedido: calcular `valor_devido` (RN-01, a partir do evento `venda`, já pronto — não recalcular a partir dos itens, isso é TP-0008/TP-0020), `valor_pago` e `situacao_pagamento` (RN-02, `dominio/quitacao.ts` TP-0009, a partir dos eventos de pagamento vinculados) e `data_limite` (do evento `venda`). Montar linha `pedido_resumo`: `{ id_pedido, valor_devido, valor_pago, data_limite, situacao_pagamento, fontes }`, onde `fontes` é `JSON.stringify` de um objeto `fonte -> codigo_externo` com as chaves em ordem fixa (`vendas`, `pagamentos`, `rastreio` — só as fontes de fato vinculadas a esse pedido).
4. Montar linhas `vinculo_codigo`: para cada vínculo (`vinculo_fonte`) e também para a própria identidade `PED-nnnnnn`, normalizar o código com `normalizarCodigo` (TP-0029, `contrato/codigo.ts`). Se dois códigos normalizados iguais apontarem para `id_pedido` diferentes, lançar erro explícito interrompendo a publicação, com mensagem citando os códigos e os dois pedidos envolvidos (SDD §5: "a publicação falha se colidirem").
5. Nenhum nome da base (cliente, nome de transportadora) nas colunas — a tradução para `Transportadora N` já ocorreu em TP-0020; esta tarefa só repassa o que já vem no evento `venda`, nunca lê a base bruta diretamente.
6. Ordenar as duas listas de saída de forma determinística antes de devolver: `pedido_resumo` por `id_pedido`; `vinculo_codigo` por `codigo` (RNF-05) — o consumidor é o escritor de SQL (TP-0040, Lote 8), fora de escopo aqui gerar o SQL em si.
7. Fora de escopo: gerar `leitura.sql`; tocar o D1/`.wrangler/state`; recalcular RN-01/RN-02 do zero (reaproveita os eventos já gravados).
