## 1. Plano de execução
1. Criar `processamento/src/publicacao/linha-do-tempo.ts`.
2. Para cada pedido (mesma leitura do event store de TP-0035), pegar todos os eventos com `id_pedido` não nulo (pagamentos sem identificação, achado `sem_identificacao`, ficam de fora — critério de aceite).
3. Ordenar os eventos de cada pedido pela ordem canônica (RN-07, `dominio/ordenacao.ts`, TP-0007) e atribuir `posicao` = índice 0, 1, 2… nessa ordem — nunca pela `ordem_chegada` gravada (RN-07/G-07).
4. Marcar `fora_de_ordem` (0/1) por evento comparando a ordem de chegada gravada (`ordem_chegada`) com a canônica, reaproveitando `dominio/fora-de-ordem.ts` (TP-0013) — essa função já expõe a marca booleana por evento, conforme seu próprio plano de execução; não recalcular a lógica aqui.
5. Montar linha: `{ id_pedido, posicao, codigo_evento, fonte, tipo, momento_fato, versao_schema, dados, fora_de_ordem }`, onde `dados` é `JSON.stringify` do mesmo objeto de evento gravado no event store (TP-0018), com chaves em ordem fixa — não reprocessar nem recalcular valores do evento.
6. Ordenar as linhas finais por `(id_pedido, posicao)` (PK da tabela, SDD §5) para determinismo do SQL multi-linha gerado depois (TP-0040, fora de escopo aqui).
7. Fora de escopo: gerar o SQL; persistir achado `fora_de_ordem` em `achado_qualidade` (essa tarefa só calcula a marca para a projeção, não grava achado — ver TP-0038 para o documento `qualidade`, que recalcula os mesmos achados a partir da mesma função de domínio).
