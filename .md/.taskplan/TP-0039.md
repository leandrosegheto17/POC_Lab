# TP-0039 — Projeção dos documentos `resumo` e `indicadores`

Reserva: Livre
ID no TASK.md: TP-0039 · Lote: Lote 7 · Agente: executor · Chapéu: Backend · Est: 1h · Dep: TP-0030, TP-0031, TP-0032, TP-0033, TP-0034 · Status no TASK.md: Pendente
Reqs: RF-08, RF-11 · Aceite: `resumo` com data de corte, semente, versão do contrato, identificador da publicação (hash do conteúdo) e totais do TP-0034; `indicadores` com os blocos do TP-0033; ambos passam nos esquemas do contrato

## 1. Plano de execução
1. Criar `processamento/src/publicacao/documentos.ts`.
2. Montar documento `resumo`: `{ dataCorte, semente, versaoContrato: 'v1', identificadorPublicacao, totais }`:
   - `dataCorte` = maior `momento_fato` existente (RN-14, mesmo critério usado em TP-0016).
   - `semente` = a semente usada pelo gerador nesta execução (recebida como argumento desta função, não lida de novo — vem do `pnpm gerar --semente`, padrão `20261007` por TASK.md §1).
   - `versaoContrato` = constante `'v1'` (a API `/api/v1` nunca muda de forma, G-21; este campo é informativo, não dispara lógica).
   - `totais` = saída de `dominio/totais.ts` (`totaisResumo`, TP-0034), recebida como argumento.
   - `identificadorPublicacao` = hash SHA-256 (`node:crypto`, `createHash('sha256')` — nativo, permitido em `publicacao/` por não ser `dominio/`/`contrato/`) sobre uma representação determinística do conteúdo publicado (ex. `JSON.stringify` com chaves ordenadas de `totais` + dos blocos de `indicadores` + do documento `qualidade`, concatenados) — nunca sobre `Date.now()` ou algo não determinístico (RNF-05/ADR-002).
3. Validar `resumo` contra `contrato/resumo.ts` (TP-0030) antes de devolver.
4. Montar documento `indicadores`: `{ blocos: [indicadorEntregasNoPrazo(...), indicadorDivergenciasPorTipo(...)] }` (TP-0033), como lista — aceita itens novos dos Lotes 15/18 sem mudar a forma (L-08).
5. Validar `indicadores` contra `contrato/indicadores.ts` (TP-0031) antes de devolver.
6. Esta tarefa só produz os objetos JSON finais de `resumo` e `indicadores`; a gravação na tabela `documento` (chave/conteúdo) e a geração do SQL são do Lote 8 (TP-0040/44), fora de escopo aqui. O documento `qualidade` é produzido por TP-0038 (tarefa separada) — esta tarefa recebe o conteúdo já pronto de `qualidade` só para entrar no hash do `identificadorPublicacao`, sem reprocessá-lo.
7. Fora de escopo: indicadores Should (TP-0068/69, Lote 15) e sugestões de IA (Lote 18) — eles só acrescentam itens à mesma lista depois, sem recriar esta função.

## 2. Plano de teste
`processamento/test/publicacao/documentos.test.ts`:
- `resumo` passa no esquema `contrato/resumo.ts` (TP-0030).
- `indicadores` passa no esquema `contrato/indicadores.ts` (TP-0031).
- `dataCorte` = maior `momento_fato` de uma fixture de eventos.
- `identificadorPublicacao` determinístico: mesma entrada (totais + indicadores + qualidade fixos) chamada 2x → mesmo hash.
- Mudar 1 byte de um dos documentos de entrada → hash diferente (sensibilidade básica do hash).
- `versaoContrato === 'v1'` sempre.
Comando: `pnpm --filter processamento test publicacao/documentos`

## 3. Plano de validação de segurança
Sem I/O de rede. O hash é só identificador de conteúdo (não é segredo, não protege nada — não é controle de segurança, é determinismo/cache-busting). Verificar: nenhuma dependência nova (`node:crypto` é nativo); nenhum segredo nem log de dado sensível; `resumo`/`indicadores` não trazem nome de terceiros (G-11, já garantido pelas camadas anteriores).
