# TP-0041 — Esqueleto do Worker e `pnpm dev` com site + API

Reserva: Livre

Reqs: ADR-014, SDD §2 · Aceite: `web/worker/index.ts` com app Hono; `web/wrangler.jsonc` com `main`, `assets` (`not_found_handling: "single-page-application"`, `run_worker_first: ["/api/*"]`), `d1_databases` com binding `DB` (`poc-lab`), `compatibility_date` fixa, sem segredos; `@cloudflare/vite-plugin` no `vite.config`; `pnpm dev` sobe site e API num processo; dependências `hono`, `zod`, `@hono/zod-validator`, `wrangler`, `@cloudflare/workers-types`

## 1. Plano de execução
1. Adicionar ao `web/package.json` as dependências novas listadas em G-17 (lista fechada, nenhuma outra): `hono`, `zod`, `@hono/zod-validator`, `wrangler`, `@cloudflare/vite-plugin`, `@cloudflare/workers-types` (dev). `zod` pode já existir via `processamento`; confirmar versão compatível (zod 4, SDD §3).
2. Criar `web/worker/index.ts`: `const app = new Hono()`; por ora sem rotas de negócio (rotas reais entram no Lote 9, TP-0046 a TP-0050) — só o esqueleto que responde algo em `/api/` para o teste de fumaça (ex.: nenhuma rota ainda, deixando o 404 central do TP-0042 cobrir; mas TP-0042 é tarefa separada e paralela — aqui o mínimo é o app Hono exportado como `export default app` para o Worker).
3. Criar/editar `web/wrangler.jsonc`: `main: "worker/index.ts"`, `compatibility_date` fixa (data real, ex. do dia do SDD), `assets: { directory: "./dist/client" (ou pasta do build do Vite), not_found_handling: "single-page-application", run_worker_first: ["/api/*"] }`, `d1_databases: [{ binding: "DB", database_name: "poc-lab", database_id: "<placeholder local>" }]`. Sem `database_id` remoto real aqui (isso é ação do autor no Lote 14, TP-0065) — usar id de desenvolvimento local gerado pelo `wrangler d1 create` ou placeholder documentado. Nenhum segredo, nenhum outro binding (G-01, G-22).
4. Editar `web/vite.config.ts`: adicionar plugin `@cloudflare/vite-plugin` (SDD §3, risco mitigado pelo plano B `vite build --watch` + `wrangler dev` se a integração falhar — registrar BK se precisar do plano B).
5. Confirmar que `pnpm --filter web dev` (ou script raiz `pnpm dev`, TASK.md §1 "Comandos") sobe site + API num único processo, usando a mesma pasta de estado `.wrangler/state` que `wrangler d1 execute --local` (risco do SDD §6; verificado de fato só no TP-0044, aqui só preparar o terreno).
6. Fronteiras (G-03): `web/worker` só importa `dominio`/`contrato` do `processamento` e `node:*` fica restrito a `test/`; `web/src` não importa `web/worker`. Não implementar lógica de rota, erro ou cabeçalho aqui — isso é TP-0042 (paralelo).
7. Fora de escopo: rotas reais (Lote 9), carga de dados no D1 (TP-0044), deploy remoto (TP-0065).
