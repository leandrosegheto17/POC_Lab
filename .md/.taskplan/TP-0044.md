## 1. Plano de execução
1. Depende de todas as projeções do Lote 7 já concluídas (TP-0035 a TP-0039: `pedido_resumo`/`vinculo_codigo`, `linha_do_tempo`, `divergencia`, `qualidade`, `resumo`/`indicadores`) e do escritor de SQL (TP-0040) e do esqueleto do Worker/`wrangler.jsonc` (TP-0041, para apontar para o mesmo binding `poc-lab`/mesma pasta `.wrangler/state`).
2. Criar `processamento/src/publicacao/publicar.ts`: orquestra — chama as funções de projeção do Lote 7 sobre o event store local (lido de `armazenamento/`), monta o mapa tabela→linhas, chama o escritor (TP-0040) com o DDL de `publicacao/leitura-d1.sql` (TP-0032), e escreve o resultado em `dados/publicacao/leitura.sql` (fora do git, igual a `dados/origem/`).
3. Criar `processamento/src/cli/publicar-dados.ts`: chama `publicar.ts`, depois invoca `wrangler d1 execute poc-lab --local --file dados/publicacao/leitura.sql` **no diretório do pacote `web`** (para usar o `wrangler.jsonc` e a pasta `.wrangler/state` do TP-0041 — risco do SDD §6 "plugin do Vite e wrangler usarem pastas diferentes"; se a invocação `--local --file` falhar por caminho relativo, resolver com `cwd` explícito no `spawn`/`execFile`, não com cópia de arquivo).
4. Tratamento de falha: se o processo `wrangler` sair com código ≠ 0, a CLI falha com mensagem clara (stdout/stderr do wrangler + contexto, nunca ocultando o erro) — "sem conta" significa que o `--local` não exige `wrangler login`; não adicionar fallback de autenticação aqui.
5. Script `pnpm publicar-dados` (ou integrado só via `preparar`, conforme TASK.md §1 "Comandos: no máximo 3" — `publicar-dados` é passo interno de `pnpm preparar`, TP-0045, não necessariamente um script de primeiro nível exposto ao usuário; registrar no `package.json` como script interno se necessário para o teste).
6. Nenhum segredo, nenhuma chamada remota aqui (G-01, G-22) — é sempre `--local`. Publicação remota é outra tarefa (TP-0065, Lote 14) e nunca parte do CI (G-16).
7. Fora de escopo: não reimplementar as projeções (Lote 7, já prontas) nem o escritor (TP-0040); não tocar `wrangler.jsonc` além de usá-lo.

Verificado:

Achado 1 (baixa, não crítico): `shell: true` com `path.resolve(...)` sem aspas. Com o shell, o argumento é concatenado numa linha de comando; checkout em pasta com espaço ou metacaractere (`&`, `(`, `%`) quebra a carga (ou executa fragmento) no Windows. Risco só do próprio autor, por isso baixa. Não coberto por RTP existente. RTP-0038: ver proposta abaixo.
- Proposta: título "publicar-dados: não usar shell:true no spawn do wrangler"; aceite: `executarWrangler` não passa `shell: true` (usa `pnpm.cmd` no win32 ou `process.execPath` + bin do wrangler) e teste com caminho contendo espaço e `&` chama o executor com o argumento intacto; arquivos: `processamento/src/cli/publicar-dados.ts`, `processamento/test/integracao/publicacao.test.ts`; comando: `pnpm --filter processamento exec vitest run test/integracao/publicacao.test.ts`.

Resumo para o relatório: APROVADA, 0 críticos e 1 não crítico (baixa: shell:true no spawn do wrangler com caminho sem aspas, RTP-0038); só --local, sem env/segredo, leitura apenas no event store.
