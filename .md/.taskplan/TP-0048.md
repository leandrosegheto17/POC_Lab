# TP-0048 — Endpoint `GET /api/v1/pedidos/{codigo}/linha-do-tempo`

Reserva: Livre
ID no TASK.md: TP-0048 · Lote: Lote 9 · Agente: executor · Chapéu: Backend · Est: 3h · Dep: TP-0030, TP-0042, TP-0043 · Status no TASK.md: Pendente
Reqs: RF-05, M2, ADR-016 · Aceite: Normaliza o código (`normalizarCodigo`), resolve por `vinculo_codigo`, lê `pedido_resumo` e `linha_do_tempo` por índice (≤ 2 consultas); eventos em ordem canônica na forma v1 (passam pelo esquema v1, sem `versao_schema` nem campo posterior); devolve o código buscado; inexistente → 404 `pedido_nao_encontrado`; fora do padrão (> 40 caracteres, `'`, `%`, `;`) → 400; teste com `' OR 1=1 --` não devolve outro pedido

## 1. Plano de execução
1. Depende de TP-0029 (`normalizarCodigo`, `EsquemaParametroCodigo` em `contrato/codigo.ts`), TP-0030 (`EsquemaLinhaDoTempoV1`/`EsquemaEventoV1` em `contrato/linha-do-tempo-v1.ts`), TP-0042 (`problema()`, hook de validação) e TP-0043 (D1 de teste com `vinculo_codigo` apontando 2 fontes para o mesmo `id_pedido`, SDD §5).
2. Em `web/worker/consultas.ts` (compartilhado — ler antes de editar, `Edit` nunca `Write`): adicionar `resolverPedido(db, codigoNormalizado)` = `SELECT id_pedido FROM vinculo_codigo WHERE codigo = ?` (PK, SDD §5 linha 171) — cobre tanto código de fonte quanto a própria identidade `PED-nnnnnn` (TP-0035 grava ambos); `buscarPedidoResumo(db, idPedido)` = `SELECT * FROM pedido_resumo WHERE id_pedido = ?` (PK); `listarLinhaDoTempo(db, idPedido)` = `SELECT * FROM linha_do_tempo WHERE id_pedido = ? ORDER BY posicao` (usa a PK composta `(id_pedido, posicao)`, já em ordem canônica desde a projeção TP-0036 — não reordenar aqui). Todas com `.bind(...)`, nunca concatenação (G-08).
3. Criar `web/worker/rotas/linha-do-tempo.ts`: path param `:codigo` validado por `zValidator('param', z.object({ codigo: EsquemaParametroCodigo }))` — `EsquemaParametroCodigo` já restringe a `[A-Za-z0-9 _-]` até 40 caracteres (TP-0029), então `'`, `%`, `;` e qualquer string > 40 chars falham **antes** de chegar à consulta → 400 `parametro_invalido` (hook de TP-0042). Handler: `codigoNormalizado = normalizarCodigo(codigo)` → `resolverPedido` (1ª consulta); se não encontrar linha, `problema('pedido_nao_encontrado', 404)`; senão, em paralelo (`Promise.all`), `buscarPedidoResumo(idPedido)` + `listarLinhaDoTempo(idPedido)` (2ª e 3ª consulta lógicas, mas o critério de aceite diz "≤ 2 consultas" contando a resolução — reconferir: resolução (1) + resumo (2) + eventos (3) são 3 roundtrips; se o critério exige ≤ 2 no total, uma opção é um único `SELECT` com `JOIN` de `vinculo_codigo` + `pedido_resumo`, e separado o `SELECT` de `linha_do_tempo` — ou seja, resolver `id_pedido` e `pedido_resumo` numa consulta só via `JOIN`, mais a de eventos = 2 consultas totais). **Decisão desta tarefa:** usar `SELECT pr.* FROM vinculo_codigo vc JOIN pedido_resumo pr ON pr.id_pedido = vc.id_pedido WHERE vc.codigo = ?` como a 1ª consulta (resolve + resumo juntos) e `listarLinhaDoTempo` como a 2ª — bate com "≤ 2 consultas" do critério de aceite; se essa junção não encontrar linha, é `pedido_nao_encontrado`.
4. Montar a resposta na forma v1: `pedido: { identidade: id_pedido, codigoBuscado: codigo (original, não normalizado — "devolve o código buscado"), fontes: JSON.parse(pedido_resumo.fontes) convertido em array {fonte, codigo}, devido: valor_devido, pago: valor_pago, dataLimite: data_limite, divergencias: [...] }` — para `divergencias` desta tela, consultar a tabela `divergencia` por `id_pedido` (SDD §5, "+ divergências" do critério da rota) — se isso adicionar uma 3ª consulta, registrar a decisão: o critério de aceite da tarefa fala em "≤ 2 consultas" para resumo/linha do tempo; a consulta de divergências é adicional e já prevista no SDD §2 ("Pedido ... + divergências"), não conta no mesmo orçamento — documentar essa leitura no código com comentário citando SDD §2 linha 85.
5. `eventos`: cada linha de `linha_do_tempo` vira um evento na forma v1 — `JSON.parse(dados)` (payload do evento) + campos de cabeçalho (`tipo`, `momento_fato`, `fonte`) + `chegouForaDeOrdem: !!fora_de_ordem`, **sem** `versao_schema` (é descartado pelo `.parse()` do `EsquemaEventoV1`, TP-0030, que não é `.strict()`); validar a lista final com `EsquemaLinhaDoTempoV1.parse(...)` antes de `c.json(...)` — isso garante mecanicamente que nenhum campo posterior (ex. `meio_pagamento` de v2) escapa para a v1 (G-21).
6. Registrar a rota em `web/worker/index.ts`, atenção à ordem de registro das rotas (`/api/v1/pedidos/:codigo/linha-do-tempo` não deve colidir com outra rota literal).
7. Fora de escopo: `/api/v2` (TP-0076/77, Should/Lote 17); schema/projeções (`vinculo_codigo`, `pedido_resumo`, `linha_do_tempo`, `divergencia` — Lote 7, já prontas).

## 2. Plano de teste
`web/test/worker/linha-do-tempo.test.ts` com `app.request()` e D1 de teste (TP-0043, dados com 1 código alternativo apontando para o mesmo `id_pedido` que `PED-`):
- GET com `PED-000001` → 200, corpo passa `EsquemaLinhaDoTempoV1.safeParse`, `pedido.codigoBuscado === 'PED-000001'`, eventos em ordem canônica.
- GET com o código alternativo da fonte (ex. código de vendas) apontando para o mesmo pedido → 200, mesmo `pedido.identidade`, `codigoBuscado` igual ao código alternativo enviado (não normalizado na resposta).
- GET com variação de caixa/espaço (`" ped-000001 "`) → resolve igual (via `normalizarCodigo`), 200.
- GET com código inexistente válido no formato (`PED-999999`) → 404, corpo `codigo: 'pedido_nao_encontrado'`.
- GET com código > 40 caracteres → 400 `parametro_invalido`, nunca chega à consulta.
- GET com `' OR 1=1 --` (contém `'`, espaço, `=`) → 400 `parametro_invalido` (falha no `EsquemaParametroCodigo`, regex `[A-Za-z0-9 _-]` rejeita `'`, `=`) — teste explícito confirmando que a resposta **não** é 200 com outro pedido (critério de aceite literal).
- GET com `%` e `;` isolados em string de outra forma válida → 400.
- Evento de pagamento v1 no dataset sem `versao_schema` na resposta e sem `meio_pagamento` mesmo que a fixture tenha gravado um campo extra no `dados` (reforça G-21 no nível da rota, não só do esquema isolado — TP-0030 já testa o esquema, aqui testa a integração real).
Comando: `pnpm --filter web test linha-do-tempo`

## 3. Plano de validação de segurança
Esta é a rota de maior superfície da tarefa (M2, busca de usuário com texto livre) — G-08 crítico aqui: (a) `EsquemaParametroCodigo` fecha o alfabeto de entrada antes de qualquer SQL (defesa 1); (b) toda consulta usa `prepare(CONSTANTE).bind(idPedido/codigo)`, nunca concatenação (defesa 2, a real contra SQL injection); checar literalmente no diff que nenhuma consulta desta rota usa template literal com `codigo`/`idPedido` interpolado. Teste negativo explícito com `' OR 1=1 --` é mandatório (já no plano de teste) e cobre a ameaça plausível descrita no critério de aceite. 404 nunca revela se o código existe em outra fonte (mensagem genérica `pedido_nao_encontrado`, sem detalhe de qual fonte foi tentada). Sem segredo, sem dependência nova; dado fictício (RNF-06).
