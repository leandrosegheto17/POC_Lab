# TP-0052 — `clienteApi` e gancho `useConsulta`

Reserva: Livre
ID no TASK.md: TP-0052 · Lote: Lote 10 · Agente: executor · Chapéu: Frontend · Est: 2,5h · Dep: TP-0003, TP-0029 · Status no TASK.md: Pendente
Reqs: RF-11, UX-SPEC §4 · Aceite: `fetch` com `AbortController` e tempo limite de 10 s; valida a resposta com o esquema do contrato; traduz para estado conforme a tabela do UX-SPEC §4 (200 válido, formato inesperado, 400, 404, 5xx, rede, tempo esgotado, cancelada = silenciosa); só a chamada mais recente vale; nunca expõe `detail`/status ao usuário

## 1. Plano de execução
1. Criar `web/src/dados/cliente-api.ts`: função que recebe caminho (`/api/v1/...`) e um esquema zod de resposta (de `processamento/src/contrato/`, único import permitido fora de `dominio`/`contrato`, G-03); monta `fetch` com `AbortController`, timeout 10 s (`setTimeout` chamando `controller.abort()`), parseia o corpo como JSON com try/catch (corpo não-JSON cai no mesmo balde de "formato inesperado").
2. Mapear resultado para um tipo de estado discriminado (ex. `{ tipo: 'sucesso', dados } | { tipo: 'erro', mensagem } | { tipo: 'cancelada' }`) seguindo **exatamente** a tabela da UX-SPEC §4 "Respostas da API → estado de tela": 200 válido no esquema → sucesso; 200 fora do esquema ou não-JSON → erro "Os dados recebidos estão em formato inesperado."; 400/404 → erro específico (a tradução de mensagem de 400 em T1 e 400/404 em T2 é decidida pela tela consumidora — aqui o cliente só devolve o `codigo` RFC 9457 do corpo de erro, nunca `detail`/status); 5xx → "Não foi possível consultar os dados agora. Tente de novo em alguns segundos."; falha de rede (`fetch` rejeita) → "Sem conexão com o servidor."; abort por timeout → "A consulta demorou demais."; abort por cancelamento do próprio site → estado `cancelada` silencioso (sem mensagem).
3. Usar o esquema de erro (`contrato/erro.ts`, TP-0029) para parsear o corpo de erro e extrair só o `codigo`; nunca repassar `detail`, `type`, `title` ou status HTTP para a UI (G-12, regra UX-SPEC §4 final).
4. Criar `web/src/dados/use-consulta.ts`: hook React que recebe a URL (ou `null` para não disparar) e o esquema de resposta; internamente chama `clienteApi`, mantém estado `carregando | vazio | erro | sucesso` (interpretação de "vazio" fica a cargo de quem consome — ex. lista vazia — o hook só expõe sucesso/erro/carregando; "vazio" é derivado pela tela a partir dos dados de sucesso, salvo onde a UX-SPEC já mapeia um `codigo` de erro para "vazio corrigível", que o hook deve conseguir expor via o `codigo` traduzido); cancela a chamada anterior (`AbortController.abort()`) sempre que a URL mudar ou o componente desmontar, garantindo que só a resposta da chamada mais recente atualize o estado (guarda por referência/contador de chamada).
5. Fora de escopo: telas concretas (T1–T4, Lotes 11–13) e tradução final de mensagem por tela — aqui só a infraestrutura genérica de chamada/estado. Nenhuma biblioteca de dados (TanStack Query etc., ADR-014/G-17).

## 2. Plano de teste
- `web/test/cliente-api.test.ts` com `fetch` falso (`vi.fn`/mock global): casos — 200 corpo válido (parseia e devolve sucesso); 200 corpo que falha no esquema zod (erro "formato inesperado"); 200 corpo não-JSON (mesmo erro); 400 com corpo RFC 9457 (`codigo: parametro_invalido`) — devolve só o `codigo`, nunca `detail`; 404 (`codigo: pedido_nao_encontrado`); 500 (`erro_interno` → mensagem 5xx); `fetch` rejeitando (erro de rede) → mensagem de rede; `fetch` nunca resolve dentro de 10 s (usar fake timers) → mensagem de tempo esgotado; abort manual (simulando troca de URL) → estado `cancelada` sem mensagem.
- Teste de `use-consulta` (Testing Library, `renderHook` ou componente wrapper): trocar a URL antes da primeira resposta chegar cancela a chamada anterior e só o resultado da última conta (usar duas promessas resolvidas fora de ordem para provar a guarda contra *race condition*).
- Caso de borda: nenhuma mensagem de erro do teste contém `detail`, status HTTP ou texto bruto do corpo — asserção negativa explícita.
- Comando: `pnpm --filter web test -- cliente-api` (e o arquivo de `use-consulta` se separado).

## 3. Plano de validação de segurança
- G-12: toda resposta passa pelo esquema do contrato antes de qualquer uso; nada do corpo é exibido sem passar por JSX (aqui só a camada de dados, mas a garantia de nunca vazar `detail`/status é o ponto central de segurança desta tarefa — checar no diff que nenhum campo do RFC 9457 além de `codigo` sai do `clienteApi`).
- Timeout de 10 s e cancelamento evitam chamadas penduradas consumindo requisições do Worker sem necessidade (custo variável, SDD §6) — confirmar que o `AbortController` é sempre limpo (sem *listener*/timer vazando entre chamadas).
- Nenhuma dependência nova (fetch nativo, zod já previsto); sem segredo, sem log de corpo de resposta no console em produção.
