## 1. Plano de execução
1. Criar `web/src/componentes/EstadoCarregando.tsx`: recebe a mensagem (ex. "Carregando divergências…"); renderiza dentro de uma região com `aria-live="polite"` e `aria-busy="true"`; ícone `aria-hidden` opcional + texto visível (não é só ícone, UX-SPEC §3).
2. Criar `web/src/componentes/EstadoVazio.tsx`: recebe mensagem (ex. "Nenhum pedido com divergência do tipo X.") e, opcionalmente, uma ação/link (ex. "Ir para a página 1", "Ver todas as divergências") — usar a paleta "Sem divergência" (`#86efac`/`#0f2417`/`#1f5133`) conforme alias da UX-SPEC §3, com ícone `aria-hidden`.
3. Criar `web/src/componentes/EstadoErro.tsx`: recebe mensagem e um `onTentarDeNovo`; usa a paleta "Pago duas vezes" como alias de erro (UX-SPEC §3); `role="alert"` **só quando o erro interrompe a tela toda** (prop booleana, ex. `interrompe`, default `true`, para permitir o caso da faixa de resumo que falha silenciosamente sem `role="alert"`, UX-SPEC §4 linha "Cabeçalho"); botão "Tentar de novo" que chama `onTentarDeNovo`, devolve o foco para a região de conteúdo (`ref` com `.focus()` num elemento com `tabIndex=-1` ou a própria região `aria-live`) e reanuncia "Carregando…" (ou seja, o fluxo esperado é: clique → estado volta a `EstadoCarregando` → a região `aria-live` already existente recebe o novo texto, que o leitor de tela anuncia).
4. Os três componentes compartilham a mesma região `aria-live="polite"` por tela (um único contêiner que troca de conteúdo entre carregando/vazio/erro/sucesso) — aqui construir os componentes de forma que a tela-mãe (T1–T4, Lotes 12–13) possa compô-los dentro de uma única região; não criar a região global aqui (isso é responsabilidade de cada tela consumidora), mas garantir que os componentes aceitem ser renderizados dentro de uma `aria-live` externa sem duplicar `aria-live` interno quando não for o topo.
5. Ícones SVG próprios (`aria-hidden="true"`, traço 1,5 px, 20 px) para vazio/erro, reaproveitando ou criando em `web/src/componentes/icones/` se ainda não existir (coordenar com TP-0055, que também usa ícones — aqui criar só os ícones mínimos que estes 3 componentes precisam, sem duplicar se o diretório já existir de outra tarefa paralela; se colidir, preferir nome de arquivo específico destes componentes e revisar depois).
6. Fora de escopo: a lógica de repetir a chamada real (é o hook `useConsulta`/`clienteApi` do TP-0052, usado pela tela) — aqui `EstadoErro` só expõe o callback `onTentarDeNovo`, que a tela-mãe implementa.

## 2. Plano de teste
- `web/test/estados.test.tsx` (Testing Library + jsdom):
  - `EstadoCarregando`: renderiza mensagem; `aria-busy="true"` presente; contêiner com `aria-live="polite"` (se for o próprio componente a declarar) ou aceita ser filho de uma região externa (testar as duas formas de uso conforme decisão do passo 4).
  - `EstadoVazio`: renderiza mensagem e, quando fornecido, o link/ação; sem link quando não fornecido.
  - `EstadoErro`: `role="alert"` presente quando `interrompe` (padrão); ausente quando `interrompe={false}`; clique em "Tentar de novo" chama `onTentarDeNovo` (mock) exatamente uma vez; foco é movido para o elemento esperado após o clique (`expect(elemento).toHaveFocus()`).
  - `vitest-axe` sobre cada um dos três componentes isoladamente, incluindo a variante `EstadoErro` com e sem `role="alert"`: `expect(resultados).toHaveNoViolations()`.
- Caso de borda: mensagem vazia/ausente não deve quebrar a renderização (ainda que não seja um caso de uso real, garantir que o componente não lança).
- Comando: `pnpm --filter web test -- estados`.

## 3. Plano de validação de segurança

- Sem rede, sem input de usuário além do clique em "Tentar de novo" (callback controlado pela tela-mãe); sem dependência nova.
- Sem segredos, sem log.
