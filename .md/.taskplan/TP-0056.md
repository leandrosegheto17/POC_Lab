# TP-0056 — Faixa de resumo e contexto do resumo

Reserva: Livre
ID no TASK.md: TP-0056 · Lote: Lote 11 · Agente: executor · Chapéu: Frontend · Est: 1,5h · Dep: TP-0030, TP-0052, TP-0055 · Status no TASK.md: Pendente
Reqs: RF-11, UX-SPEC §2, §4 · Aceite: Consulta `/api/v1/resumo` uma vez por carga do app e compartilha por contexto; faixa "Dados sintéticos · corte AAAA-MM-DD · N pedidos"; enquanto carrega ou se falhar, só "Dados sintéticos", sem anúncio nem erro

## 1. Plano de execução
1. `web/src/dados/contexto-resumo.tsx`: `React.createContext` + `ProvedorResumo` que chama `useConsulta` (TP-0052, `web/src/dados/use-consulta.ts`) sobre `GET /api/v1/resumo` uma única vez na montagem (sem refetch por rota/navegação) e expõe `{ resumo, estado }` aos consumidores via `useContext`. Envolver a árvore em `App.tsx`/`Casca.tsx` (TP-0055) com `ProvedorResumo` no nível mais alto que não force remonte entre rotas.
2. `web/src/componentes/FaixaResumo.tsx`: consome o contexto; enquanto `estado === 'carregando'` ou `estado === 'erro'`, renderiza só "Dados sintéticos" (UX-SPEC §2: "sem anúncio nem erro" — logo, sem `aria-live`, sem `role="alert"`, texto estático); em sucesso, "Dados sintéticos · corte {resumo.dataCorte} · {N} pedidos" com `N` = `resumo.totais.pedidos` (formatado conforme TP-0030/TP-0039 — confirmar nome exato do campo no esquema `contrato/resumo.ts` do TP-0030 ao integrar; se o campo for outro nome, usar o do esquema real, não inventar).
3. Esta faixa NÃO é focável e não entra na ordem de foco (UX-SPEC §6) — não usar `tabIndex` nem landmark novo; é só texto dentro do `header`/`aside` da `Casca`.
4. Formatação de data: `AAAA-MM-DD` direto do campo (sem conversão de fuso, UX-SPEC §3 "Formatação"); número de pedidos com `Intl.NumberFormat('pt-BR')` se o UX-SPEC pedir separador de milhar (consistente com moeda/contagens do design system).
5. Integrar o slot deixado em `Casca.tsx` pelo TP-0055 (rodando em paralelo nesta rodada): se `Casca.tsx` ainda não tiver o slot ao editar, adicionar o `ProvedorResumo`/`FaixaResumo` no ponto estrutural equivalente e registrar a integração ao final; não reescrever o layout de `Casca.tsx` feito pelo TP-0055 além do necessário para encaixar a faixa.
6. A tarefa não marca "Concluída" enquanto a integração com `GET /api/v1/resumo` depender de mock — se o endpoint real (TP-0046/TP-0049 etc., Lote 9) ainda não estiver publicado, implementar contra o esquema do TP-0030 (mock-aware, UX-SPEC/EXECUTION-FLOW) e registrar a pendência.
7. Fora de escopo: cartões de resumo e chips (`CartoesResumo`/`FiltroTipo`, Lote 12, TP-0058); esta tarefa só prepara o contexto compartilhado e a faixa textual do cabeçalho.

## 2. Plano de teste
- `web/test/faixa-resumo.test.tsx`: com `fetch` falso (padrão do TP-0052/`clienteApi`), três casos: (a) resposta 200 válida → faixa mostra data de corte e total; (b) pendente/carregando → só "Dados sintéticos"; (c) erro (500 ou rede) → só "Dados sintéticos", sem `role="alert"`/`aria-live` disparado.
- Confirma que `GET /api/v1/resumo` é chamado exatamente uma vez mesmo que o componente consumidor seja renderizado em múltiplos pontos da árvore (contexto compartilhado, não múltiplas chamadas).
- `vitest-axe` na faixa nos 3 estados, sem violação.
- Rodar: `pnpm --filter web test faixa-resumo`.

## 3. Plano de validação de segurança
Tarefa de leitura de dados públicos via API já validada por esquema (G-12: toda resposta passa pelo esquema do contrato, aplicado dentro de `useConsulta`/`clienteApi` do TP-0052). Verificar no diff: nenhum `dangerouslySetInnerHTML`; texto da API renderizado só por JSX; nenhuma informação de erro técnico (`detail`, status) exposta na faixa, conforme UX-SPEC §4 ("sem anúncio nem erro" é tratamento de UX, mas também evita vazar detalhe de erro ao usuário). Nenhum segredo, nenhuma dependência nova.
