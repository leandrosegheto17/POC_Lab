## 1. Plano de execução
1. Criar `web/src/paginas/Divergencias.tsx`, rota já registrada por TP-0055 em `App.tsx` (rota raiz `/`). Lê `tipo` da URL (`useSearchParams`/equivalente do roteador escolhido em TP-0055); valores aceitos = `duplicado|parcial|pago_nao_enviado|enviado_nao_pago|entrega_atrasada` ou ausente ("Todos"); qualquer outro valor é tratado client-side como estado "Vazio corrigível" com a mensagem fixa do UX-SPEC §4, SEM chamar a API (evita round-trip 400 previsível) — mas se a API ainda assim devolver 400 `parametro_invalido`, tratar igual via `clienteApi`/`useConsulta` de TP-0052.
2. Chamar `GET /api/v1/divergencias?tipo=&pagina=1&tamanho=50` via `useConsulta` (TP-0052); esta tarefa não implementa paginação na URL (isso é TP-0060) — usar `pagina=1` fixo aqui; TP-0060 vai estender para ler `?pagina=`. Documentar essa divisão: TP-0059 entrega a tela funcional com página 1 fixa; TP-0060 acrescenta a navegação entre páginas.
3. `<h1>` "Divergências (N pedidos)" — N = `paginacao.total` da resposta.
4. Renderizar `CartoesResumo` e `FiltroTipo` (TP-0058) acima da tabela, alimentados pelo contexto do resumo (TP-0056). Trocar o filtro chama `aoMudar` de `FiltroTipo`, que atualiza a URL (`?tipo=...`, sem o parâmetro quando "Todos") via navegação do roteador — isso dispara nova renderização e nova chamada à API.
5. `TabelaDados` (TP-0054) com `<caption>` "Pedidos com divergência — filtro: <rótulo> — página 1 de <totalPaginas>" (rótulo = "Todos" ou o rótulo do tipo); colunas Pedido (link para `/pedido/:codigo` via `pedido`), Tipo (`EtiquetaTipo`), Motivo (texto), Eventos (`<details><summary>▸ ver N eventos</summary>` com lista dos `eventos[]`: tipo, momento_fato, fonte, código).
6. 4 estados do UX-SPEC §4/tabela da seção "Respostas da API → estado de tela": carregando ("Carregando divergências…", `aria-busy`, `aria-live="polite"`), vazio (sem itens no filtro: "Nenhum pedido com divergência do tipo X."), erro (mensagem conforme tabela + "Tentar de novo"), sucesso (tabela). 400 `parametro_invalido` → estado vazio corrigível: "O filtro do endereço não é válido. [Ver todas as divergências]" com link que limpa `?tipo=`.
7. Cancelamento: ao trocar filtro, a chamada anterior em andamento é cancelada (feature já do `useConsulta`/TP-0052 — só garantir que a chave de consulta inclui `tipo` para disparar novo efeito/cancelamento).
8. `<title>` "Divergências — POC_Lab"; foco no `<h1>` ao entrar na rota (padrão já definido em TP-0055, reaproveitar o mecanismo da Casca).
9. Fora de escopo: paginação na URL, foco no `<caption>` ao trocar de página, anúncio "50 de N..." (tudo isso é TP-0060); estado em uma data (T2); qualquer rota que não seja `/`.

## 2. Plano de teste
- `web/test/divergencias.test.tsx` (Vitest + Testing Library + `vitest-axe`, `fetch` falso via `msw` ou stub conforme padrão de TP-0052):
  - Sucesso: mock de `/api/v1/divergencias` retorna dados; `<h1>` mostra o total; tabela renderiza linhas com link para `/pedido/:codigo`, `EtiquetaTipo` certa, motivo e `<details>` com eventos; `<caption>` com filtro "Todos" e página 1.
  - Filtro: renderiza com `?tipo=duplicado` na URL inicial → chama a API com `tipo=duplicado`; selecionar outro chip atualiza a URL e refaz a chamada (verificar nova URL e novo corpo da chamada mockada).
  - Vazio (filtro sem itens): resposta com `dados: []` → "Nenhum pedido com divergência do tipo X."
  - Erro 400 `parametro_invalido`: mock retorna 400 → mensagem fixa "O filtro do endereço não é válido." com link "Ver todas as divergências" que navega para `/` sem `tipo`.
  - Erro 5xx / rede / timeout: mensagem + "Tentar de novo" que refaz a chamada (reusa cobertura de TP-0053, aqui só integração na tela).
  - Carregando: `aria-busy="true"` na região da tabela durante a chamada pendente.
  - axe sem violação crítica/séria nos 4 estados.
- Dados/fixtures: usar os tipos reais do contrato (`duplicado`, `parcial`, etc.) e nomes de campo em português (`pedido`, `tipo`, `motivo`, `eventos`).
- Comando: `pnpm --filter web test divergencias`.

## 3. Plano de validação de segurança
Superfície relevante: texto vindo da API (motivo, códigos) é renderizado só por JSX, nunca `dangerouslySetInnerHTML` (G-12) — checar no diff que `motivo` e campos de evento não passam por innerHTML. Parâmetro `tipo` da URL é validado no cliente contra a enumeração fixa antes de repassar à API (nenhuma montagem de SQL/URL livre; `useConsulta`/`clienteApi` já encapsula a query string). Nenhum dado sensível/pessoal exposto (dados sintéticos). Sem autenticação/autorização aplicável (API pública só leitura). Checar que nenhuma mensagem de erro técnica (`detail`, status, SQL) chega à tela (G-13/UX-SPEC §4) — só os textos fixos mapeados.
