# TP-0062 — Tela T2 Linha do tempo do pedido (sem estado em data)

Reserva: Livre
ID no TASK.md: TP-0062 · Lote: 13 · Agente: executor · Chapéu: Frontend · Est: 2,5h · Dep: TP-0030, TP-0052, TP-0053, TP-0055, TP-0061 · Status no TASK.md: Pendente
Reqs: RF-05, M2, UX-SPEC T2, §4 · Aceite: Chama `/api/v1/pedidos/{codigo}/linha-do-tempo`; `<h1>` com a identidade e "Encontrado pelo código X" quando buscado por código de fonte; "Aparece em N de 3 fontes" com códigos; devido, pago, data limite; etiquetas de divergência ou "Sem divergência"; 404/400 → "Pedido não encontrado" + formatos aceitos, anunciado; 4 estados; axe sem violação

## 1. Plano de execução
1. Criar `web/src/paginas/LinhaDoTempo.tsx`, montado na rota `/pedido/:codigo` (já registrada por TP-0055 em `App.tsx`; o parâmetro `:codigo` é o que `CampoBusca`/TP-0057 escreve na URL). Lê `codigo` do roteador e chama `GET /api/v1/pedidos/{codigo}/linha-do-tempo` via `useConsulta`/`clienteApi` (TP-0052) com o esquema `EsquemaLinhaDoTempoV1` (`contrato/linha-do-tempo-v1.ts`, TP-0030) — **uma única chamada** traz cabeçalho e eventos (UX-SPEC §2, sem chamada separada para o cabeçalho).
2. `<h1>` "Pedido {pedido.identidade}"; se `pedido.codigoBuscado !== pedido.identidade` (buscou por código de fonte, não pela identidade `PED-nnnnnn`), acrescenta a linha "Encontrado pelo código {pedido.codigoBuscado}".
3. Linha "Aparece em N de 3 fontes": N = `pedido.fontes.length`; lista `fonte: codigo` para cada item de `pedido.fontes` usando o rótulo em português da fonte (mesmo mapeamento de `EtiquetaFonte`/TP-0054: `vendas`→"Vendas" etc., texto "fonte: …" do wireframe, ex. "vendas (10248) · pagamentos (TX-88812) · rastreio (RS-5521)").
4. Linha "Valor devido {R$}  ·  Pago {R$}  ·  Data limite {data}": `pedido.devido`/`pedido.pago` formatados com `Intl.NumberFormat('pt-BR')` (moeda, consistente com TP-0056/UX-SPEC §3), `pedido.dataLimite` em `AAAA-MM-DD` direto do campo, todos em mono (JetBrains Mono).
5. "Situação": uma `EtiquetaTipo` (TP-0054) por item de `pedido.divergencias` (cada item tem `tipo`/`motivo`); se `pedido.divergencias` estiver vazio, mostrar o alias "Sem divergência" (paleta verde da UX-SPEC §3, mesma convenção de `EstadoVazio`).
6. Renderizar `<LinhaDoTempo eventos={eventos} />` (componente de TP-0061) com `eventos` vindo direto da resposta — não reordenar (já vem em ordem canônica RN-07).
7. 4 estados (UX-SPEC §4 tabela "T2" + tabela "Respostas da API → estado de tela"): carregando ("Buscando pedido…", `aria-busy`, `aria-live="polite"` — reaproveitar `EstadoCarregando`/TP-0053); erro 404 `pedido_nao_encontrado` ou 400 `parametro_invalido` no código → tratar como **estado "vazio"**, não "erro": mensagem fixa "Pedido não encontrado" + dica dos formatos aceitos (`PED-nnnnnn`, código de vendas, transação `TX-`, rastreio `RS-`; texto exato a definir com base nos formatos reais do domínio, sem expor `detail`/`codigo` técnico), anunciada pela região `aria-live` da tela (reaproveitar `EstadoVazio`/TP-0053, não `EstadoErro`, já que não há "Tentar de novo" útil para um código inexistente); demais falhas (5xx, rede, timeout) → `EstadoErro` com a mensagem mapeada por `clienteApi` (TP-0052) + "Tentar de novo"; sucesso → cabeçalho + `LinhaDoTempo`.
8. `<title>` "Pedido {identidade} — POC_Lab" (ou "Pedido não encontrado — POC_Lab" no caso vazio, seguindo o padrão de título único por rota, UX-SPEC §5); foco no `<h1>` ao entrar na rota (mecanismo já estabelecido por TP-0055/Casca).
9. Fora de escopo nesta tarefa: `SeletorData`/"estado em uma data" (RF-06, Should, Lote 16, TP-0072/TP-0073 — o espaço reservado no wireframe UX-SPEC §2 para "Ver estado em uma data" não entra aqui); qualquer alteração em `LinhaDoTempo.tsx` (componente) feita por TP-0061 além de consumi-lo via props.

## 2. Plano de teste
- `web/test/linha-do-tempo.test.tsx` (Vitest + Testing Library + `vitest-axe`, `fetch` falso conforme padrão de TP-0052):
  - Sucesso buscando pela identidade: mock retorna `pedido.codigoBuscado === pedido.identidade` → `<h1>` sem a linha "Encontrado pelo código"; mostra fontes, devido/pago/data limite, divergências e a `LinhaDoTempo` com os eventos do mock.
  - Sucesso buscando por código de fonte: `codigoBuscado !== identidade` → mostra "Encontrado pelo código {codigoBuscado}".
  - Sem divergência: `pedido.divergencias: []` → mostra "Sem divergência".
  - Com divergência: `pedido.divergencias` com 1+ itens → uma `EtiquetaTipo` por tipo.
  - Vazio (404 `pedido_nao_encontrado`): mensagem "Pedido não encontrado" + dica dos formatos, anunciada pela região `aria-live` (sem `role="alert"` de `EstadoErro`, sem botão "Tentar de novo").
  - Vazio (400 `parametro_invalido`): mesma mensagem (trata igual ao 404 nesta tela, UX-SPEC §4 linha "400/404 em T2").
  - Erro 5xx / rede / timeout: `EstadoErro` + "Tentar de novo" que refaz a chamada.
  - Carregando: "Buscando pedido…", `aria-busy="true"`.
  - axe sem violação crítica/séria nos 4 estados.
- Dados/fixtures: usar a forma real de `EsquemaLinhaDoTempoV1` (camelCase, `pedido.fontes[]`, `eventos[]` com `chegouForaDeOrdem`).
- Comando: `pnpm --filter web test -- linha-do-tempo`.

## 3. Plano de validação de segurança
Superfície relevante: `codigo` da rota (`:codigo`) vai direto como parâmetro de caminho para `clienteApi`/`fetch` — conferir que é só interpolado na URL sem montagem de HTML/SQL (a validação de formato é responsabilidade do backend/TP-0046, esta tela só repassa a string). Texto vindo da API (`identidade`, `codigoBuscado`, `motivo`, códigos de evento) renderizado só por JSX, nunca `dangerouslySetInnerHTML` (G-12) — checar no diff. Nenhuma mensagem técnica (`detail`, status, `codigo` RFC 9457 bruto) chega à tela: 404/400 mapeiam para o texto fixo "Pedido não encontrado", nunca repassam o `codigo` original. Sem dado pessoal (dados sintéticos); sem autenticação/autorização aplicável (API pública só leitura); sem dependência nova.
