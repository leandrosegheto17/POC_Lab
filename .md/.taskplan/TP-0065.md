3. Adicionar script `publicar` ao `package.json` raiz (ou do pacote `web`, conforme onde `preparar`/`dev` já vivem): encadeia, nesta ordem fixa, `preparar` (TP-0045) → `vite build` (pacote `web`) → `wrangler d1 execute poc-lab --remote --file dados/publicacao/leitura.sql` → `wrangler deploy`. D1 sempre antes do Worker (ADR-015, para o código novo nunca ler tabelas antigas).
4. Nenhum passo de CI dispara isto (G-16/ADR-015: publicação é só manual, pelo autor, com `wrangler login` local).
5. Documentar (nesta tarefa ou junto de TP-0066/TP-0067, mas o critério de aceite exige aqui) as ações únicas do autor antes do primeiro `pnpm publicar`: `wrangler login`, `wrangler d1 create poc-lab` (uma vez só, guardar o `database_id` gerado em `wrangler.jsonc`), configurar alerta de uso no painel do Cloudflare (SDD §7 "Custo como risco de disponibilidade").
6. Depois do deploy real (ação do autor, fora do escopo de código): rodar a conferência manual listada no critério de aceite — `curl` nas 5 rotas v1 (`resumo`, `divergencias`, `pedidos/{codigo}/linha-do-tempo`, `indicadores`, `qualidade`) + uma rota inexistente (404) + um método não-GET (405), confirmando os cabeçalhos de G-13/TP-0042; abrir T1–T4 no link publicado; colar o link no README (consumido por TP-0066/TP-0067, que também tocam README — coordenar para não sobrescrever).
7. Fora de escopo: qualquer lógica nova de rota ou regra de negócio; mudar a ordem de carga (sempre D1 → Worker); criar segredo do Cloudflare no repo ou no CI.
8. Dependências: todas as rotas (Lote 9), telas Must (TP-0057, TP-0060, TP-0062, TP-0063, TP-0064) e `preparar` (TP-0045) precisam estar prontas e testadas antes de rodar a conferência fim a fim; o código deste TP (scripts, `wrangler.jsonc`, `_headers`) pode ser escrito em paralelo, mas a conferência manual do critério de aceite só é possível depois.

## 2. Plano de teste
- Não há teste automatizado novo: o critério de aceite é "conferência manual registrada (ação do autor)". Nenhum teste de unidade/integração substitui o deploy real (que exige conta Cloudflare).
- Verificação local possível sem conta: `pnpm preparar` e `vite build` continuam verdes (já cobertos por TP-0045/TP-0041); conferir que o script `publicar` monta os 4 comandos na ordem certa (revisão do `package.json`, não execução real nesta etapa).
- Depois do deploy real do autor: registrar na resposta/nota da tarefa os resultados dos `curl` (status, `Content-Type`, cabeçalhos de segurança) das 5 rotas + 404 + 405, e confirmar visualmente T1–T4 no link. Esse registro escrito é a evidência de aceite, não um arquivo de teste automatizado.
- Caso de borda: método não-GET numa rota existente deve dar 405 com `Allow: GET, HEAD` (G-08/TP-0042); rota inexistente sob `/api/` deve dar 404 `rota_nao_encontrada` (RFC 9457).

## 3. Plano de validação de segurança
- G-01/G-22: `database_id` não é segredo, mas confirmar que nenhuma credencial do Cloudflare (token, API key) aparece em `wrangler.jsonc`, `package.json` ou no script `publicar` — autenticação é só via `wrangler login` local, nunca variável de ambiente commitada.
- G-13: `_headers` dos assets exatamente com os 3 cabeçalhos do SDD §7; respostas do Worker já cobertas em TP-0042 — aqui só confirmar via `curl` real pós-deploy que os cabeçalhos chegam de fato (nosniff, no-referrer, CSP, e nas 200 `Cache-Control: public, max-age=60`), sem CORS.
- G-16/ADR-015: nenhum passo de deploy no CI; script `publicar` só roda localmente pelo autor com `wrangler login`.
- G-22: confirmar que nenhum binding/produto Cloudflare novo foi adicionado além de Workers + static assets + D1 já previstos.
- Ameaça plausível: exposição acidental de erro interno do D1/Worker no `curl` de conferência — confirmar que erros seguem RFC 9457 genérico (TP-0042), sem pilha/SQL na resposta real.
