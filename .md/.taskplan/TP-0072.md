# TP-0072 — Componente `SeletorData`

Reserva: Livre
ID no TASK.md: TP-0072 · Lote: Lote 16 · Agente: executor · Chapéu: Frontend · Est: 1h · Dep: TP-0051 · Status no TASK.md: Pendente
Reqs: RF-06, UX-SPEC §3, §5 · Aceite: `<input type="date">` com `<label>`, botões Ver estado e Limpar; contorno com `--cor-borda-controle`; axe sem violação

## 1. Plano de execução
1. Criar `web/src/componentes/SeletorData.tsx`, componente controlado: props `valor: string`, `onMudar(valor: string): void`, `onVerEstado(): void`, `onLimpar(): void` (ou equivalente — decisão de implementação, documentar se divergir).
2. Markup conforme UX-SPEC T2 (linha 77): `<label>` visível associado ao `<input type="date">` por `htmlFor`/`id` (texto "Ver estado em uma data"), botão "Ver estado" e botão "Limpar" ao lado.
3. Estilo: contorno do `<input>` usa o token `--cor-borda-controle` (`#6b7a89`, UX-SPEC §3 linha 131) — mesmo padrão de campo de texto/campo de data já definido para os tokens do TP-0051; não inventar token novo.
4. Botão "Limpar" some/fica desabilitado quando não há valor (decisão pequena de UX não coberta explicitamente — usar `aria-disabled` e manter focável, seguindo o padrão já definido em UX-SPEC §6 linha 218 para botões desabilitados durante carga).
5. Foco visível em todos os controles (UX-SPEC §5 linha 215: contorno 3px, contraste ≥ 3:1) — herda do tema global do TP-0051, não redefinir aqui.
6. Sem chamada à API, sem lógica de domínio aqui — este componente só captura a data e dispara os callbacks; o cálculo do estado é escopo do TP-0073.
7. Fora de escopo: não integrar com `LinhaDoTempo.tsx` (TP-0073); não usar `dominio/estado.ts` diretamente aqui.
8. Depende de TP-0051 (tokens/fontes do Modelo B) já aplicados no projeto — confirmar que o token `--cor-borda-controle` existe antes de usar.

## 2. Plano de teste
`web/test/seletor-data.test.tsx` (Testing Library + vitest-axe):
- Renderiza `<label>` associado ao `<input type="date">` (`getByLabelText`).
- Digitar/selecionar uma data chama `onMudar` com o valor no formato `YYYY-MM-DD`.
- Clicar em "Ver estado" chama `onVerEstado`.
- Clicar em "Limpar" chama `onLimpar` e (se o componente for controlado via prop) o valor exibido reflete o estado vazio.
- Contorno do `<input>` usa a variável CSS `--cor-borda-controle` (snapshot de estilo computado ou verificação de classe/token, conforme padrão já usado nos outros testes de componente do projeto).
- `vitest-axe`: sem violação crítica ou séria (G-14).
- Todos os controles acessíveis por teclado (Tab alcança input, botão Ver estado, botão Limpar).
Comando: `pnpm --filter web test seletor-data`

## Verificação (2026-10-08)
Comando: `pnpm --filter web test seletor-data`.
Resultado antes: 4 de 7 testes falhando (`getByRole`/`getByLabelText` encontravam múltiplos elementos — `TestingLibraryElementError: Found multiple elements`). Causa: `web/vite.config.ts` não define `test.globals: true`, então o auto-cleanup do `@testing-library/react` entre testes não é registrado, e o DOM acumula uma instância de `<SeletorData>` por `it` dentro do mesmo arquivo.
Correção aplicada: em `web/test/seletor-data.test.tsx`, import de `afterEach`/`cleanup` e `afterEach(cleanup)` explícito no topo do arquivo (escopo local do teste, sem tocar `vite.config.ts`/`test/setup.ts`, que são compartilhados com outras tarefas).
Resultado final: 7/7 testes passando. Código do componente (`web/src/componentes/SeletorData.tsx`) não precisou de alteração — já atendia ao critério de aceite (label associado, botões Ver estado/Limpar, `aria-disabled` em Limpar quando vazio, sem violação de axe).

## 3. Plano de validação de segurança
Componente de UI sem I/O, sem chamada à API e sem dado vindo do servidor — superfície de segurança mínima: nenhuma dependência nova (G-17, confirmar `package.json` do `web` inalterado); nenhum `dangerouslySetInnerHTML` (G-12); sem segredo, sem log. `<input type="date">` nativo evita parsing manual de texto livre, reduzindo risco de entrada malformada ser propagada (o valor segue como string de data do próprio input).
