Reserva: Livre

Reqs: RF-09, ADR-006 · Aceite: União passa a aceitar `pagamento` v2 (aditivo); o consumidor de saldo/quitação v1 não muda e dá o mesmo resultado sobre uma mistura de v1 e v2

## 1. Plano de execução
1. Ler `processamento/src/dominio/evento.ts` (TP-0006) imediatamente antes de editar — é arquivo compartilhado entre lotes; usar `Edit`, nunca `Write`.
2. Na união discriminada do `tipo: 'pagamento'`, acrescentar a variante v2 por `versao_schema`: `{ tipo: 'pagamento', versao_schema: 2, valor: number, referencia_original: string, meio_pagamento: string }` — mesmos campos da v1 + `meio_pagamento` (SDD §5 linha 178, ADR-006: "v2 adiciona `meio_pagamento`"). A v1 (`versao_schema: 1`) continua exatamente como está — nenhum campo removido/renomeado (G-15).
3. Não tocar nas variantes `venda`/`coleta`/`transporte`/`entrega` nem em `dominio/modelo.ts` — fora de escopo desta tarefa.
4. Confirmar que `dominio/quitacao.ts` (TP-0009, `calcularQuitacao`) já recebe só `pagamentos: number[]` (valores já extraídos) — ou seja, quem monta essa lista a partir de `Evento[]` é outra camada (consumidor de saldo). Esta tarefa não precisa alterar `quitacao.ts`; precisa garantir que o tipo `pagamento` v2 ainda expõe `valor: number` no mesmo formato da v1, de modo que qualquer código que hoje faz `evento.valor` (ignorando `meio_pagamento`) continue funcionando sem mudança — é a prova de ADR-006 ("o consumidor de saldo lê só `valor` e não muda").
5. Fora de escopo: gerador/adaptador de pagamentos (TP-0075), esquema zod/contrato da API v2 (TP-0076), rota (TP-0077). Esta tarefa é só o tipo TypeScript puro em `dominio/`.
6. Atenção: sem I/O, sem `node:*`, sem `zod` em `dominio/` (G-02) — a variante v2 é só um literal de tipo, sem validação de runtime aqui.
