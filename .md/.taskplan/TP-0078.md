# TP-0078 — Teste `validação: contrato v1 e v2` e demonstração no README

Reserva: Livre

Reqs: RF-09, ADR-016, M4 · Aceite: Para o mesmo pedido, a resposta da v1 é idêntica com os pagamentos gravados como v1 ou como v2 e passa no esquema v1; a v2 traz `meio_pagamento`; o site não muda (testes do `web` verdes sem alteração); README mostra os 2 `curl` e tira o item de "fora de propósito"

## 1. Plano de execução
1. Depende de TP-0075 (importação grava pagamento v1 ou v2 conforme `meio_pagamento` no CSV) e TP-0077 (rota v2 publicada e funcionando).
2. Criar `web/test/worker/contrato-v1-v2.test.ts` com o teste nomeado exatamente `validação: contrato v1 e v2` (TASK.md exige o nome exato, mesmo padrão de `validação: idempotência` do TP-0027) — usar `app.request()` e o D1 de teste (TP-0043).
3. Montar 2 fixtures do **mesmo pedido** (mesmo `id_pedido`, mesmos demais eventos), diferindo só na versão do pagamento gravado em `linha_do_tempo`: fixture A com o pagamento como v1 (`versao_schema: 1`, sem `meio_pagamento`); fixture B com o mesmo valor de pagamento gravado como v2 (`versao_schema: 2`, `meio_pagamento` preenchido). Chamar `GET /api/v1/pedidos/{codigo}/linha-do-tempo` contra as duas fixtures e comparar as respostas — devem ser **idênticas** byte a byte (ou por igualdade estrutural profunda) e ambas passam em `EsquemaLinhaDoTempoV1.safeParse` (TP-0030) — é a prova central de ADR-006/G-21: a v1 nunca muda de forma, independente da versão gravada internamente.
4. Chamar `GET /api/v2/pedidos/{codigo}/linha-do-tempo` contra a fixture B (pagamento v2) e confirmar que a resposta traz `meioPagamento` no evento de pagamento e passa em `EsquemaLinhaDoTempoV2.safeParse` (TP-0076).
5. "O site não muda": não alterar nenhum arquivo em `web/src/` nesta tarefa; rodar a suíte existente do `web` relacionada ao consumo da API v1 (ex. `web/test/*.test.tsx` que usam `clienteApi`/linha do tempo) **apenas os arquivos já afetados por este lote** (não a suíte inteira, conforme modo de trabalho) e confirmar que passam sem alteração de expectativa — evidência de que a v2 é aditiva e invisível ao site (que só lê `/api/v1`, TASK §1 linha 54).
6. Atualizar `README.md` (ler antes de editar, `Edit`, arquivo compartilhado entre tarefas de documentação — TP-0066/67 já escreveram outras seções): na seção da API (TP-0067), acrescentar um exemplo `curl` para `/api/v1/...` e outro para `/api/v2/...` do mesmo pedido, mostrando a mesma identidade com formas diferentes (v1 sem `meioPagamento`, v2 com). Remover/atualizar o item "contrato v2 pendente" da lista de "fora de propósito"/pendências do README (nota deixada pelo TP-0067, linha "versão no caminho — `/api/v2` chega no Lote 17... ainda não publicado") para refletir que agora está entregue.
7. Fora de escopo: qualquer mudança em `web/src/`, em `dominio/evento.ts` (TP-0074, já pronto), nos esquemas de contrato (TP-0076, já pronto) ou na rota em si (TP-0077, já pronta) — esta tarefa só valida e documenta.

## 2. Plano de teste
(O "Plano de teste" desta tarefa é o próprio "Plano de execução" passos 3–5, já que a tarefa **é** o teste de validação — TASK.md a lista com a coluna Testes igual ao nome do teste.)
- `web/test/worker/contrato-v1-v2.test.ts`, teste `validação: contrato v1 e v2`:
  - v1 idêntica entre fixture A (pagamento v1) e fixture B (pagamento v2), ambas válidas no esquema v1.
  - v2 traz `meioPagamento` e `versaoSchema` corretos para a fixture B.
  - Caso de borda: pedido com **mistura** de pagamentos v1 e v2 (ex. 2 transações, uma de cada versão) — v1 soma/exibe ambos igual (saldo correto, TP-0074 passo 4), v2 mostra cada evento com sua própria versão.
- Regressão do `web`: reexecutar só os testes de tela/consumo de API já existentes que tocam a linha do tempo v1 (ex. `web/test/*linha-do-tempo*`, `web/test/*LinhaDoTempo*`) sem alteração de expectativa.
- Comando: `pnpm --filter web test contrato-v1-v2` e, para a regressão, `pnpm --filter web test -- <arquivos de tela afetados>` (não a suíte inteira).
- Verificação manual do README: rodar os 2 `curl` documentados contra `pnpm dev` local e confirmar que o formato bate com o que está escrito (mesmo padrão de verificação do TP-0067).

## 3. Plano de validação de segurança
Tarefa de teste + documentação, sem código de produção novo — mas é o teste que **prova** G-21 (v1 não muda de forma) e ADR-006 (compatibilidade v1/v2), então a revisão central aqui é de corretude da garantia, não de superfície de ataque nova:
- Confirmar que o teste compara a resposta v1 das duas fixtures por igualdade estrutural real (não um `toBeDefined()` frouxo) — é a única forma de o teste efetivamente pegar uma regressão de G-21.
- Confirmar que os exemplos `curl` do README não expõem nada sensível (dado é sintético, sem autenticação, mesma observação do TP-0067) e não usam valor malicioso como exemplo "normal".
- Sem segredo, sem dependência nova (G-17), sem dado pessoal.
