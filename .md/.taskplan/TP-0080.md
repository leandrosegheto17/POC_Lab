# TP-0080 — RN-11 conferência da sugestão

Reserva: Livre
ID no TASK.md: TP-0080 · Lote: Lote 18 · Agente: executor · Chapéu: Backend · Est: 1,5h · Dep: TP-0009 · Status no TASK.md: Pendente
Reqs: RN-11 · Aceite: Conferida só se o valor for compatível com o saldo em aberto, a data do pagamento ≥ data do pedido e o pedido não estiver quitado; devolve o motivo em texto

## 1. Plano de execução
1. Criar `processamento/src/dominio/conferencia-sugestao.ts`, puro (sem I/O, sem `node:*`, roda nos 3 lugares — regra do TASK.md §1).
2. Assinatura: `conferirSugestao(pedidoCandidato: { devido: number; pago: number; dataPedido: string }, sugestao: { valor: number; dataPagamento: string }): { conferida: boolean; motivo: string }`. `devido`/`pago` vêm de RN-01/RN-02 (TP-0008/TP-0009, já calculados pelo chamador); `dataPedido`/`dataPagamento` em ISO-8601.
3. 3 condições, todas obrigatórias para `conferida: true` (RN-11):
   - **Valor compatível com o saldo em aberto**: `saldoEmAberto = devido - pago`; compatível quando `Math.abs(saldoEmAberto - sugestao.valor) <= 0.01` — reaproveita a mesma tolerância de R$ 0,01 de RN-02 (TP-0009), por consistência de regra de negócio (decisão de detalhe, não PENDENTE: RN-11 não fixa o valor da tolerância, RN-02 já fixa 0,01 para o mesmo tipo de comparação monetária).
   - **Data do pagamento ≥ data do pedido**: comparação de string ISO-8601 (ordenável lexicograficamente) ou `Date`, sem `Date.now()` (determinismo, G-10) — comparar só as 2 datas recebidas.
   - **Pedido não quitado**: reaproveitar a situação de RN-02 (TP-0009, `quitacao.ts`) — se o chamador já calculou a situação, passar `situacao !== 'quitado'`, ou recalcular aqui chamando a função pura de TP-0009 (preferir reaproveitar para não duplicar regra).
4. `motivo` sempre em texto simples com os valores, nos 2 casos (conferida e rejeitada) — ex. "Valor compatível (R$ X ≈ saldo R$ Y), pagamento em {data} após o pedido em {data}, pedido ainda não quitado." para conferida; para rejeitada, apontar exatamente qual das 3 condições falhou e os valores envolvidos (mesmo padrão de `motivo` das divergências RN-03 a RN-06, TASK.md §1 "Domínio e regras").
5. Fora de escopo: decidir *quais* pedidos são candidatos (isso é L-03, parte de TP-0081); chamar IA ou cache (TP-0081/TP-0082); qualquer I/O.

## 2. Plano de teste
`processamento/test/dominio/conferencia-sugestao.test.ts` (unidade):
- Caso conferida: valor dentro de 0,01 do saldo em aberto, data do pagamento ≥ data do pedido, situação ≠ quitado → `conferida: true`, motivo cita os valores.
- Caso rejeitada por valor: saldo em aberto muito diferente do valor sugerido → `conferida: false`, motivo aponta a incompatibilidade de valor.
- Caso rejeitada por data: data do pagamento < data do pedido → `conferida: false`, motivo aponta a data.
- Caso rejeitada por quitação: pedido já quitado → `conferida: false`, motivo aponta que já está quitado.
- Borda: diferença de exatamente R$ 0,01 → ainda compatível (tolerância inclusiva, mesma convenção de RN-02); diferença de R$ 0,011 → incompatível.
- Borda: data do pagamento exatamente igual à data do pedido → compatível (`≥`, não `>`).
Comando: `pnpm --filter processamento test -- dominio/conferencia-sugestao`.

## 3. Plano de validação de segurança
