# TP-0081 — Porta `ProvedorSugestao`, provedor falso e caso de uso `sugerir`

Reserva: Livre
ID no TASK.md: TP-0081 · Lote: Lote 18 · Agente: executor · Chapéu: Backend · Est: 2,5h · Dep: TP-0027, TP-0079, TP-0080 · Status no TASK.md: Pendente
Reqs: RF-10, ADR-010 · Aceite: Monta candidatos (§6 L-03); cache por SHA-256 de texto + candidatos ordenados + modelo; respeita `IA_TETO_CHAMADAS` (padrão 20); sem chave ou teto atingido = "sem sugestão" e segue; testes só com provedor falso

## 1. Plano de execução
1. Criar `processamento/src/ia/porta.ts`: interface `ProvedorSugestao` com um único método, ex. `sugerir(texto: string, candidatos: string[], modelo: string): Promise<string | null>` (devolve a identidade escolhida entre `candidatos` ou `null` = "sem sugestão"). É a única porta do projeto (TASK.md §1: "A única porta é `ProvedorSugestao`").
2. Criar `processamento/src/ia/provedor-falso.ts`: implementação determinística para teste — ex. recebe um mapa configurável `texto → identidade escolhida` (ou devolve sempre `null`/o primeiro candidato, conforme o teste pedir); nunca faz rede.
3. Criar `processamento/src/ia/sugerir.ts`, caso de uso que orquestra (lê o event store via `armazenamento/`, nunca SQL fora de lá — G-05):
   - **Candidatos (L-03, SDD §6):** para cada pagamento com achado `sem_identificacao` (TP-0021/TP-0010), montar a lista de pedidos candidatos = pedidos não quitados (RN-02, via TP-0009), com `data do pedido ≤ data do pagamento` e `saldo em aberto ≥ valor pago − R$ 0,01`, até 20, ordenados pela diferença de saldo (menor diferença primeiro — decisão de detalhe: "ordenados pela diferença de saldo" não especifica direção; menor diferença primeiro é a leitura natural de "melhor candidato primeiro", documentar a escolha).
   - **Cache:** calcular `chave = sha256(texto + JSON dos candidatos ordenados + modelo)` (usar `node:crypto` — permitido em `ia/`, que não é `dominio/`); antes de chamar o provedor, checar `obterCache(chave)` (TP-0079); se existir, devolver a resposta cacheada sem chamar o provedor nem consumir o teto.
   - **Teto:** ler `IA_TETO_CHAMADAS` do ambiente (padrão `20`, `process.env`, permitido em `ia/` e `cli/`); manter contador de chamadas efetivas (não cacheadas) nesta execução; ao atingir o teto, todo pagamento restante vira "sem sugestão" sem chamar o provedor (e sem gravar cache, pois não houve resposta real).
   - **Sem chave:** se não houver provedor configurado (chamador passa o provedor; a ausência de chave é decidida por quem monta o provedor em TP-0083, não aqui) — esta função recebe o `ProvedorSugestao` já pronto (injeção simples por parâmetro) e, se for `undefined`/omitido, todo pagamento vira "sem sugestão" imediatamente.
   - Para cada sugestão aceita pelo provedor, aplicar `conferirSugestao` (TP-0080, `dominio/conferencia-sugestao.ts`) usando o pedido escolhido como candidato; gravar o resultado (identidade sugerida, conferida, motivo) — decidir aqui o formato interno de retorno da função `sugerir` (lista de `{ pagamento, textoReferencia, pedidoSugerido, conferida, motivo }` por pagamento sem identificação), que TP-0084 vai consumir.
   - Gravar no `cache_ia` (TP-0079, `gravarCache`) a resposta recebida do provedor (não a decisão de `conferirSugestao`, que é sempre recalculada — RN-11 é regra, não cabe em cache).
4. Nenhuma chamada de rede aqui: quem faz `fetch` é o provedor real (TP-0082), injetado por quem monta a CLI (TP-0083). Esta tarefa só define a porta, o provedor falso e a orquestração.
5. Fora de escopo: provedor real via `fetch` (TP-0082); CLI/variáveis de ambiente de chave (TP-0083, exceto `IA_TETO_CHAMADAS` que já é lido aqui); projeção no documento `qualidade` (TP-0084).

## 2. Plano de teste
`processamento/test/ia/sugerir.test.ts` (só com `provedor-falso.ts`, sem rede — G-09):
- Candidatos: fixture com pedidos não quitados, data e saldo variados → lista de candidatos respeita os 3 filtros de L-03 e o teto de 20, ordenada pela diferença de saldo.
- Cache: 2 chamadas com o mesmo texto/candidatos/modelo → a segunda não invoca o provedor falso (instrumentar um contador no fake) e devolve a mesma resposta.
- Teto: configurar `IA_TETO_CHAMADAS=2` (ou passar como parâmetro, se a função aceitar override de ambiente para teste) com 3 pagamentos sem identificação → o 3º vira "sem sugestão" sem chamar o provedor.
- Sem provedor (`undefined`): todos os pagamentos viram "sem sugestão", nenhuma chamada, nenhuma gravação de cache.
- Conferência: provedor falso devolve uma identidade de candidato → resultado passa por `conferirSugestao` (TP-0080) e o `conferida`/`motivo` batem com o esperado (casos conferida e rejeitada).
- Provedor falso devolve `null` → "sem sugestão", sem chamar `conferirSugestao`.
Comando: `pnpm --filter processamento test -- ia/sugerir`.

## 3. Plano de validação de segurança
G-09 central aqui: a IA (mesmo o provedor falso) nunca vincula sozinha — só escolhe entre os candidatos enviados, e a decisão final depende de `conferirSugestao` (RN-11); a sugestão nunca entra nos indicadores (fora de escopo desta tarefa, mas a função não deve escrever em nenhuma estrutura de indicador). Checar no diff que `sugerir.ts` só é chamado localmente (CLI, TP-0083), nunca do Worker/site (G-09, G-22) — esta tarefa não expõe nada à API. `IA_TETO_CHAMADAS` lido só de variável de ambiente, nenhum valor hardcoded de chave. Sem dependência nova (`node:crypto` é nativo).
